# 突发卡顿与原生崩溃排查

2026-09-06，`codex/lightweight-path-tracing`。以下区分已经证实的代码问题、运行时观测和
尚未排除的原因；不同采集中的视距、场景和窗口尺寸有变化，不用平均 FPS 作前后对比。

## 已落实的改动

| 路径 | 问题及处理 |
| --- | --- |
| ByteBuffer 上传 | LWJGL `memAddress(buffer)` 已含 position；再次相加会从错误位置读数据。两处上传统一使用 remaining 区间，并覆盖非零 position、slice 和只读 view。此错误已确认，但不能据此认定原生崩溃已修复。 |
| 地形 CPU 翻译 | 移除每次 `BuiltinMaterialClass.values()` 的数组副本；27 邻域查询复用单个局部 probe；FaceGrid 复用 4096 槽数组；小分组使用小容量 IdentityHashMap；坐标键混合 hash，避免规则网格造成大量 HashMap 树节点。已插入 map 的键不再修改，probe 不插入 map。 |
| 空区块实体遍历 | 大视距下每帧仍检查所有相关区块，但空集合直接跳过 values view 和 iterator。不能裁掉视锥外、仍可被光线命中的方块实体。 |
| 静态场景上传 | 每帧目标由 64 MiB 降为 8 MiB，并限制至 4 个 cluster；不可拆的大 cluster 单独推进。此预算限制帧内工作量，不等于显存上限。 |
| BLAS 压缩 | 保留 64 MiB 在途目标内存预算，另设 8 MiB、16 项的每帧预算；大 BLAS 单独推进，保持 FIFO 和在途资源契约。 |
| 材质表 | MaterialId 只追加；上传追加区间，不在每次动态场景更新时重新复制整个表。发布成功才推进游标，失败可重试，旧帧仍可读取原有区间。 |
| Surface 表发布 | `HashSet.removeAll(List)` 在两者等长的常见整批上传中选择逐项 List.contains，退化到 O(n²)。JFR 中 `SurfaceRecords.uploaded` 占 719/2320 个主线程采样；改为逐项 hash 删除，保持 O(n) 和快照之外脏项的语义。 |
| GC | 开发运行改用 ZGC，目的是降低加载时的停顿。它没有消除本机原生崩溃，发行 JAR 不能替外部启动器选择 GC。 |

原 G1 采集出现约 7–21 ms 的 young GC 停顿，地形加载时可每 0.5–1 秒发生。
后续 ZGC 的正常暂停降到约百分之一毫秒量级，但大量分配仍消耗 CPU 和内存带宽。
JFR 中还有 Minecraft 光照存储的 `Long2ObjectOpenHashMap.clone` 大量分配；它不是 Prime
路径追踪状态分配。崩溃期间的长 safepoint 不作为正常帧卡顿的证据。

## 原生崩溃证据

**状态：已记录，按用户要求暂停排查。** CPU/内存稳定性由用户择时复测；当前不能认定
JVM 或硬件中的哪一方是根因，不宣称崩溃已修复，不继续试启动参数。另一个非 Java 的短时
数据校验在收到暂停指示后已中断，没有可用通过/失败结论。

| 运行 | 结果 |
| --- | --- |
| Oracle 25.0.2，G1，游戏 | 约 239 秒，G1 并发线程崩溃，现场有损坏的引用。 |
| Temurin 25.0.4，G1，游戏 | 约 266 秒，GC worker 崩溃。更新到该版本未消除问题。 |
| Temurin 25.0.4，ZGC，游戏 | 约 402 秒，C2 编译的 `SectionMeshAccumulator.emitTriangle` 读取损坏的材质引用。 |
| Temurin 25.0.4，ZGC，纯 CPU JMH | 约 112 秒，`ClusterSceneTranslator.translateSection` 崩溃。 |
| 相同纯 CPU 配置复测 | 约 184 秒，`CpuClusterMesh.fromSegments` 崩溃。 |
| 关闭 `ReduceAllocationMerges` 的纯 CPU 长测 | 约 425 秒，`ClusterSceneTranslator.translateSection` 再次崩溃，排除该选项作为修复。 |
| 仅 C1 的纯 CPU 测试 | 10 分钟通过；分配速率约 15 GiB/s，低于 C2 的约 47 GiB/s，不能单凭此结果认定 C2 是根因。后段和客户端启动重叠，吞吐不用于性能对比。 |
| 正常 C2 客户端，启用分段计时 | 约 156 秒，原版服务端 `TicketStorage.shouldKeepDimensionActive` 的解释执行代码发生坏引用访问；崩溃位置并不局限在 Prime 翻译器。 |

纯 CPU 复现使用 `ClusterTranslationBenchmark` 的 extreme corpus、16 workers、8 GiB heap、
`-Djoml.nounsafe=true`。崩溃日志的已加载 DLL 中没有 Vulkan、NVIDIA、LWJGL 或 Prime 原生库。
因此 GPU 提交或 Prime JNI 不是复现该类损坏的必要条件；仍需区分 JVM/JIT/GC 缺陷和平台稳定性。
普通 Java 对象越界或逻辑错误不应破坏 JVM 堆引用。崩在某个 Java 方法也不等于该方法就是写坏内存的位置。

本机为 i9-14900KF，报告 CPU 微码 0x12F，内存配置 7200 MT/s。用户确认 CPU 未超频，
内存超频曾通过稳定性测试、正常使用一年以上，近期没有重测；常驻 HWiNFO 未观察到 WHEA。
没有自动修改硬件设置。
没有 WHEA 事件不能证明平台稳定；同样，CPU 型号和内存频率本身也不能证明硬件有故障。

`ReduceAllocationMerges` 关闭后的短测曾通过，延长到 7 分钟仍崩溃。没有把这个诊断选项
设为生产默认值。后续使用 `-XX:TieredStopAtLevel=1` 区分 C2 路径；它降低吞吐，不能未经
验证就作为生产运行方案。短测通过不足以确认修复，延长测试结果与游戏验证需分别记录。
原始 JFR、JMH 输出和崩溃日志保存在本地忽略的 `build/register-analysis`、`run` 与根目录。

## GPU 长帧定位

可选 JVM 参数 `-Dprime.profileSubmissions=true` 为 realtime、static scene、dynamic scene、
BLAS compaction 写入 JFR `prime.Submission` 事件。CPU duration 是录制/提交区间；
`previousGpuNanos` 使用 Minecraft 非阻塞 TimerQuery，是前三个完成样本的滑动平均，
并非该 CPU 事件的精确配对样本。查询未完成时跳过，不为诊断等待 GPU。初始化零值应排除。
诊断默认关闭，不分裂生产 shader，也不改变路径记录或采样算法。

主线程在 `vkWaitSemaphores` 等待只能说明它在等此前 GPU 工作，不能据此断言是 PT、
BLAS 构建或上传拖慢。大视距的静态/动态 TLAS 更新、上传、压缩与实际追踪需分别看 GPU 时间。

第一段带计时的加载样本中，static scene CPU 录制/提交 p50 11.1 ms、p99 32.2 ms、
最大 147.4 ms；GPU 三样本均值的 p99 为 2.4 ms。realtime GPU 三样本均值 p99 为 4.6 ms。
该段与 CPU 压测重叠且随后暂停，绝不能作为稳态 FPS 基准；但它与 JFR 的 O(n²) 发布栈
共同说明静态场景 CPU 准备是实际尖峰来源之一，不能把整帧低帧都归因于 shader。

移除平方复杂度后的客户端采集中，该发布热点已消失。另有 67/2127 个主线程采样落在
Surface 表 HashMap 碰撞树查找，先记录为后续热点；一个逐字混合 hash 候选在合成规则 UV
数据上没有改善桶分布，因此未保留。需要先采真实 key 分布再决定，不能假定更多混合计算必然更快。

## 粒子错图

26.2 `TextureAtlas.createTexture` 使用 usage 15，包含 render-attachment 位；这个位不能证明
内容是未知编码的场景颜色。旧捕获因此拒绝 atlas，返回索引 0；普通几何把 0 当无纹理回退，
粒子却继续用自身 atlas UV 去采槽 0 的方块 atlas，可以表现为水雾上出现楼梯图案。

捕获现在用 AtlasManager 当前持有的 GPU 纹理对象确认已知 sRGB 来源，允许其 attachment
用途，仍拒绝来源未知的 render attachment。快照属于单帧 Session，不跨 reload 保存身份。
粒子回退编码为自带颜色的 constant material，保留实例与几何，不再错误采样方块 atlas。
回归覆盖已知 atlas/同属性未知纹理的身份区别，以及粒子回退经过实例化后的材质编码。
用户已在游戏中确认粒子问题修复。
