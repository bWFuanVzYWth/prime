# 旧实时渲染器寄存器与状态生命周期分析

分析日期：2026-09-05。依据用户提供的三份旧 Nsight CSV，结合当前仓库仍保留的实时路径代码。本文是新轻量渲染器的设计输入，不代表当前 primary-only 路径的测量结果，也不修改现有生产规范。

**核心判断：旧实现的高峰主要出现在“外围状态仍然存活时，进入另一个复杂计算”的交界处。** 透明散射携带 guide/PSR 和路径状态进入 BSDF；直接光携带表面、介质和后续用途的数据进入面积光采样；tail 又把这些工作放入同一个续传循环。重写应先规定每个昂贵阶段允许存活的数据，再决定模块和 dispatch 数量。

需要区分三个量：

- `# Reg`：shader 所需的寄存器分配数量；`# Warp` 是独立运行时的理论驻留 warp 上限，不是实际 occupancy。
- `Live Registers`：被报告代码范围内的存活寄存器峰值。调用者后续还要使用的值会与被调用计算的临时值重叠；不能把父子函数的峰值相加，也不能把差值精确归属到某几个变量。
- `RT Live State Bytes`：跨 trace / shader execution / reorder 边界需要保留的状态。它不是 payload ABI 大小，也不是普通 register spill 的测量，更不能直接除以 4 得到寄存器峰值。结构体可能只关联到一个源位置，而非具体成员。[NVIDIA Shader Profiler](https://docs.nvidia.com/nsight-graphics/UserGuide/shader-profiler.html)

本文中百分比均为捕获范围内的 **PC 样本占比**。pipeline 各行合计为 100%；它们不是各阶段独占 GPU 毫秒，不能直接换算可提高多少 FPS。寄存器影响还需结合实际 occupancy、eligible warps、吞吐和 spill 验证。

这份导出有几处缺陷，已在分析中绕开：

- pipeline 在 `Instruction Mix` 附近的复合列与表头错位；Top-Down 表头有 21 列，数据只有 19 列，并含 `###ERROR###`。本文只使用可确认的前部指标；pipeline 的主要 stall 从枚举位置与末尾计数交叉验证，LGSB 比例完全一致。
- 执行指令数与 active-thread 列全为 0；不能据此分析动态指令量、分支出现率或 warp 分歧。
- Top-Down 导出没有保留完整缩进层级，还有 `Multiple shaders...` 的独立根节点。不能把所有 inclusive 函数样本相加，或要求某个 `main` 行等于 pipeline 样本。
- 缺少捕获 commit、GPU 型号、驱动、Nsight 版本、完整 SASS 和实际运行配置。下文函数位置优先采用 CSV 的旧位置；当前源码用于验证数据流，不能证明与被捕获二进制完全一致。当前 position fetch、SurfaceKey 改动后的性能也不能由旧数据推算。

重写需要明确区分：当前反弹的工作状态、下一反弹必须保留的状态、只在最终输出使用的状态。上一跳 MIS 信息在消费完之后应结束生命周期；下一跳信息在 scatter 完成后再生成。累计 signal 是否留在寄存器，应结合反弹数、分支与队列开销实测。不要仅把大循环拆成几个 inline 函数，就期待其跨调用状态消失。

### Any-hit 与 resolve：不是 BSDF 的问题

`shadow_nonopaque.anyhit` 占 **9.21%** 样本，分配 **128**，源级 live 峰值 **102** 在 `primeHitTriangle`，随后 `primeResolveSurfacePrimitive` 到 **101**，alpha/base-color 路径到 **96**。同一个 `primeHitTriangle` 在 `world.closesthit` 中是 **61**、`world.anyhit` 中是 **84**。

当前 [shadow_nonopaque.anyhit.slang](C:/Users/linlin/.codex/worktrees/0039/prime/shaders/entry/hit/shadow_nonopaque.anyhit.slang:81) 依次处理源/目标身份、三角形与界面、UV/alpha、玻璃颜色、薄壁或实体介质边界。长寿命 payload 与候选几何、材质中间量叠加；这里的成本不能靠精简 BSDF 解决。对于大量候选面，缩短每次 any-hit 和减少进入昂贵路径的次数都重要。

新路径可在已有资源翻译边界给出明确的 opaque / alpha / transmissive 分类，让普通 MC 方块与简单 cutout 只进入所需逻辑，复杂边界走独立慢路径。具体能否跳过 position fetch、法线或界面解析，必须按该类材质的实际消费字段判断，不能仅凭“这是主光线”推定。

## 如何理解 stall，避免优化错对象

tail 的 NOINST 77.55% 和 landing-direct 的 56.29% 值得检查取指与代码规模，但不充分证明“指令缓存太小”。NOINST 还可能包含等待取指调度，需结合 SASS、指令缓存和活跃 warp 数据。LGSB 表示等待 local/global/texture/surface 读取的依赖；LGTHR 表示相关发射队列拥塞，不能单凭这两个指标认定显存带宽已饱和或发生寄存器 spill。[NVIDIA stall 定义](https://docs.nvidia.com/nsight-graphics/UserGuide/shader-profiler.html#stall-reasons)、[NVIDIA No Instructions 定义](https://docs.nvidia.com/cuda/archive/10.2/nsight-compute/docs/NsightCompute/index.html)

在当前数据中，应同时考虑四个优化方向：减少峰值提高并发、减少长依赖读取、缩小实际执行代码、减少进入昂贵阶段的光线数。给所有 shader 强制一个较低寄存器上限，可能只是把状态写入 local memory；未经 spill 和帧时间验证，不应作为主要架构策略。

## 新轻量渲染器的建议

### 先约束状态，再选择分阶段程度

当前 [primary.raygeneration.slang](C:/Users/linlin/.codex/worktrees/0039/prime/shaders/entry/primary/primary.raygeneration.slang:18) 只构造相机光线、trace、输出颜色；closest-hit 读取命中材质颜色。三份 CSV 不包含它的性能数据。应把它作为独立起点逐项加功能，每一步看分配量和真实 GPU 时间。

| 逻辑阶段 | 应持有的数据 | 不宜提前展开的数据 |
| --- | --- | --- |
| 相机 trace | ray、当前像素/工作索引、小 payload | BSDF、灯光 sample、完整 guide |
| 表面解析 | 当前命中身份、所需几何与材质 | 多个光源、下一跳 transport、所有输出通道 |
| 一次直接光 | receiver、当前光源、必要介质、最小输出 | 第二个光源完整 sample、下一跳 BSDF state |
| BSDF scatter | 当前材质、入射方向、随机值、必要介质 | 尚未消费的灯光域、完整历史 guide |
| 更新与输出 | 小 scatter 结果、真正要更新的 guide / signal | 已完成的采样域和 closure state |

这是**逻辑生命周期边界**，不要求五次 GPU dispatch。先在同一 entry 中缩小数据范围、延迟构造，并观察编译器产物；只有边界仍不能降低分配量，或明显需要重排时，再用固定小记录和队列隔开。大 struct 改成 `inout`、多写几个花括号、把函数标成不内联，都不是可靠的寄存器预算机制。

实质原则是 `peak = max(某时刻仍需使用的全部值)`。降低峰值要让数据真正不再被后续使用、可便宜地重算，或明确存放在阶段外；不是仅改变源代码外观。

从简单和显存出发，初版可使用固定像素索引与按需存在的续传记录；不要直接继承旧完整 wavefront 的 guide、双分支、delta-walk、tail 队列体系。仅在普通/透明路径性能差异足够大时分开，避免为每个特性组合生成一种队列和 shader。

### 显存与寄存器的取舍必须一起算

每增加一份 16 B/路径的永久记录，1080p 单路径约增加 **31.6 MiB**，4K 约 **126.6 MiB**；双分支再乘 2。一次写入、一次读取还会产生相应带宽，另有队列索引与容量余量。因而“每一阶段都落完整 surface/path”很可能抵消地形压缩收益。

小而频繁复用的全局 SurfaceKey 表适合固定记录、稳定索引和窄加载；不要为减一次查表把同一属性重新铺到每三角形。position fetch 的三角形顶点应限于重建所需位置，完成权威命中/法线等消费后结束生命周期，不向多个阶段传递九个顶点分量。表面重建、重算、窄状态缓存三者应按每路径成本比较，不能把显存节约和寄存器降低混为一谈。

### 可以接受与旧严格路径不同的策略时，优先改什么

以下是候选设计取舍，尚未实施。建议明确新轻量路径支持的行为，避免用大量运行时开关让严格/近似两套行为同时扩大同一个 entry。

| 候选 | 对应旧成本 | 代价与约束 | 建议 |
| --- | --- | --- | --- |
| 面积光先采用较简单的纹理分布或面积采样 | 123–124 的投影立体角域峰值与代码规模 | 在支持集完整且 selection/sample/PDF/MIS 一致时，可保持期望值；近距离大光源、掠射角方差可能上升 | **优先实验**；比较相同时间下的降噪后质量 |
| 透明主表面改为单条随机反射/透射续传 | 双分支结果与 guide/PSR 生命周期、额外光线和记录 | 概率与权重正确时输运期望可保持，但低样本噪声、透明历史与 guide 策略会改变 | **优先实验**，比同时持有两套分支状态简单 |
| 简化透明 guide，按需要才建立虚拟位置/方向 | scatter、delta、split、resolve 的外围状态 | 折射/镜面运动下可能出现拖影、guide 错配或细节损失 | 应和选定降噪器共同设计 |
| 简化多层介质/彩色透明阴影 | 高成本 nonopaque any-hit、payload 与边界累积 | 改变嵌套介质、玻璃接触和厚度相关透射效果 | 适合明确受限的轻量模式，优先验证常见 MC 场景 |
| 简化方向能量/BSDF 模型或扩大 LUT 近似 | BSDF 内部 state、能量变换、代码规模 | 改变高掠射、粗糙介质、混合 lobe 的能量/外观；当前能量路径已部分查表 | 排在生命周期和采样实验之后 |
| 缩窄连续着色状态、采用更简单的浮点乘积 | 部分保存状态和数学开销 | FP16 存储不保证两个值共用一个硬件寄存器；需检查 codegen、极值与溢出 | 局部实验，不先全局改精度 |

简单采样替换应同步删除旧混合分布的 PDF 回算依赖，否则只是改了采样入口，代码和寄存器压力仍可能留在 MIS 路径。树选择也要保持抽样与 PDF 使用一致的权重定义。

相较之下，精确整数身份和 BLAS f32 命中基础不是这组数据里最有说服力的第一项牺牲对象。可以先去掉确定的大生命周期与功能成本；放宽身份或改固定 epsilon 引入的漏光、自交通常更难维护，也没有这里的直接性能收益证据。

### 建议的落地顺序与验收

1. **记录新 primary-only 基线。** 保存 GPU/驱动、配置、分辨率、场景/相机、shader hash；测实际 GPU ms、VRAM、各 entry 的分配寄存器与 live 峰值。
2. **实现一条简单直接光路径。** 一次只展开一个光源；与投影立体角版本 A/B。重点看 direct 峰值、阴影 context 字节与质量，而非只比较着色指令数量。
3. **加入单条续传。** 初版避免把完整 guide/PSR 带入 scatter。分别捕获 opaque、foliage、glass/water，决定是否需要按材质类别拆开。
4. **再加入必要的 guide、透明历史与更多反弹。** 每加入一项，都记录它使哪个既有阶段的分配量上升；若某个少用分支把普通路径从较低档位推到 128，比较独立 shader 与队列成本。
5. **最后比较 SER 和更细的阶段切分。** 用实际 occupancy、eligible warps、local-memory spill、L1/L2/VRAM 吞吐及 GPU ms 验证。没有新失败或新改动，不反复扩大测试范围。

目前可以把普通 shade 的 64–96 档位作为待验证的工程目标，而非保证或跨 GPU 固定阈值。实际决策看目标设备的资源限制档位；降低几个 live 值却没有改变分配量，也没有减少等待，可能不会带来帧时间收益。

这次最值得先做的两个小型实验是：**把面积光展开移到太阳处理之后**，以及**使不变 guide/PSR 不跨越 BSDF 采样**。它们都直接对应捕获中可见的数据流。随后再比较简化面积光分布、单透明续传和轻量 guide；这样容易分清收益来自生命周期、调度还是画质取舍。
