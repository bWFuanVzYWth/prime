## 结论与顺序

进一步优化应优先改变“哪些工作由哪个阶段完成、哪些工作不必每条路径重复”，而不是继续围绕单个表达式降成本。

| 顺序 | 设计方向 | 联动范围 | 主要消除的工作 | 性质 |
| --- | --- | --- | --- | --- |
| 1 | 保持分布的灯光树编译与查询调度 | 灯光构建、GPU 布局、选灯/MIS、SER/队列 | 节点地址依赖、静态度量重复求值、分散的子树访问 | 保持原树、分支概率和随机数映射 |
| 2 | 从 SurfaceDefinition 编译专用阴影交互数据 | 场景翻译、纹理动画、材质/介质、any-hit | 每候选重新解释材质、取参考颜色、计算消光、解析相邻端点 | 保持现有语义的跨模块部分求值 |
| 3 | 按材质拓扑组织求值，独立提交阴影请求 | Wavefront、BSDF 调度、队列/暂存、RT、重建 | 完整表面在多个阶段往返；通用入口活跃状态；shadow 调用保存恢复 | 保持数学的执行架构重构 |
| 4 | SHaRC 类世界空间辐射缓存 | 场景修订、稀疏更新、路径终止、重建 | 大量路径尾部的追踪、选灯、阴影和 BSDF 工作 | 近似实时模式，不能悄悄替代现有结果 |
| 5 | 场景更新的依赖图与增量发布 | section 捕获、cluster 翻译、灯光、TLAS、descriptor | 小改动触发的大范围重编译/重绑定 | 针对移动与编辑，静止 CSV 尚不能验证 |

**建议先设计 1 和 2，再以 3 承接新的数据流。** 4 是潜在收益范围更大的独立路线，但需要接受新的误差合同。仅切换 compute、整理 SoA 或减少 descriptor 分配，不单独列为本轮主线。

## 1. 保持分布的灯光树编译与查询调度

用户明确排除：合并太阳光与面积光、以局部/全局混合分布替代当前灯光树、ReSTIR 类方法。已有实测表明前两类会劣化质量。这里保留两级树拓扑、各分支度量、原随机数映射、面内采样及独立太阳光估计。

### 1.1 把逻辑灯光树编译成面向查询的记录

当前 [tree_select](C:/WorkSpace/prime/shaders/service/light/tree_select.slang:29) 每级先读当前节点的孩子指针，再读两个孩子的分类，随后按 internal/world leaf/emitter leaf 读取度量。这种表示便于建树，但 GPU 必须逐层追踪地址依赖。

新的编译步骤可以将一个二叉决策及其两个孩子需要的热数据放入同一分支记录，并直接携带下一决策的引用。内部孩子需要原 centroid/power/direction；world leaf 需要原 cluster 根度量、translation 和子树入口；emitter leaf 引用专用几何度量记录。所有 entry 使用相同的逻辑树，只有物理布局改变。

**不能只把兄弟节点放在一起就称作新方案。** [CpuLightTree](C:/WorkSpace/prime/src/client/java/dev/prime/render/terrain/CpuLightTree.java:80) 已保证兄弟连续。进一步目标是消除“先读孩子控制字，才知道去哪里拿度量”的依赖，以及叶上的通用场景记录解释。

[world leaf](C:/WorkSpace/prime/shaders/service/light/tree_common.slang:116) 当前经过 leaf → SectionRecord → SectionLightHeader → cluster root。编译记录可直接保存所需的原始根数据和子树 binding，绑定生命周期与引用的 cluster 一起发布/退休。保留原算式 `localCentroid - (point - translation)`；不能改成先平移 centroid 再相减，以免改变浮点结果与分支选择。

此时构建层应暴露 **实际打包后的根度量**。现有 [CompiledClusterLights.Summary](C:/WorkSpace/prime/src/client/java/dev/prime/render/terrain/CompiledClusterLights.java:158) 包含 bounds/power/direction，不应未经核对就用 Summary 重新推导并声称等价。

这里单独消除 world leaf 链覆盖的采样约为 0.746%+0.455%=1.20%，不足以解释选灯的全部成本。它应与全树记录布局、查询调度联合评估。分支记录可能变大，不能无条件把所有冷字段展开到每个节点。

### 1.2 预计算节点中真正不依赖接收点的部分

[emitter metrics](C:/WorkSpace/prime/shaders/service/light/tree_common.slang:44) 每次从 corner/edge 形成三角形顶点、AABB、退化距离分支使用的 centroid/edge 项。这些量随 emitter generation 固定，可以在灯光构建时生成专用几何记录。每次查询继续用原位置和 receiver normal 计算距离、余弦界和概率。

[方向解码](C:/WorkSpace/prime/shaders/math/light_tree.slang:15) 中，packed axis 的解码/归一化、锥角的 sine/cosine 也不依赖接收点。可按离散 node mode 编译；FULL 无需方向数据，LOBE 保持原六向权重语义，AXIS/CONE 才考虑预展开。

但这不是无条件“空间换时间”：当前 LGSB 明显，展开六个 f32 权重可能比解码位域更慢。需先统计 node mode 的实际访问分布，优先消除三角形重建和昂贵的静态解码，不盲目扩大全部节点。

输出必须复现原 shader 的 f32 运算和分支。GPU 构建可共享同一纯数学函数；CPU 计算的 double→float、FMA 差异或重新归一化不能自动视为等价。若缓存了 centroid/edge 项，必须按原重建顶点后的顺序得到它们，不能代数替换为源 edge。

### 1.3 世界树选完后，按子树重排查询

当前一个 invocation 连续完成世界树和 cluster 内树。相邻 lane 的世界树结果可能指向不同 cluster，随后从多个离散 buffer、多个节点地址加载数据。可以改成：

`原世界树抽样 → 按选中 cluster 重排执行 → 原 cluster 树抽样`

每条查询携带自己的 `pathIndex、position、receiverNormal、remapped random、world PDF`，继续原分支算法。输出按原 pathIndex 写回，因此不改变样本分配，也不共享邻近接收点的概率。进入局部树仍保留原 clamp 与运算次序。

第一种实现候选是纯 hint SER：在轻量查询状态边界调用 `reorderThreadEXT(clusterKey, bits)`，然后继续局部树。Prime 已有用于命中着色的 SER；这是将它用在新的灯光查询边界。Khronos 的 [EXT_shader_invocation_reorder](https://github.com/KhronosGroup/GLSL/blob/main/extensions/ext/GLSL_EXT_shader_invocation_reorder.txt) 提供不带 HitObject 的重排形式，但仅限 raygen，重排效果由实现决定。不能同时假设这段迁到 compute 还能使用相同机制。

第二种候选是显式 GPU 分类/排序队列，适合大批查询，可与 compute、共享上层节点缓存联动。它增加 scatter/gather、排序、同步和中间存储；不预设每个 cluster 单独 dispatch。小批次/稀疏尾部保持直接遍历，可由查询数量决定执行方式而不改变分布。

验收必须包括重排的保存恢复、队列和同步成本。hint SER 可能没有净收益；它的价值是先用较小实现验证查询一致性的收益假设，再决定是否建设更大的调度系统。

### 1.4 将几层原二叉树打包为 treelet

若依赖加载仍是主因，可以将连续 2–3 层逻辑二叉树打包成小块，使这些层的孩子位置由块内索引得到，减少层与层之间的地址依赖。块内仍逐级使用原 probability、remapping 与 PDF 乘法。

这不采用新的四叉/八叉类别分布：直接对多个子树权重重新归一，通常会改变原树的概率。也不对整个大树大量投机加载；块大小需比较缓存工作集和无用读取。

[反向 MIS](C:/WorkSpace/prime/shaders/service/light/tree_pdf.slang:15) 已有 packed bit trail，应复用同一编译布局。它预先知道块内路径，可以在已知 treelet 中计算需要的地址并提前发起加载，但保持原 root-to-leaf 的概率乘法顺序。布局优化不消除 previous position/normal 的语义需求。

### 1.5 不采用的“捷径”和验证顺序

- 不缓存 cell/tile 代表点的最终分支概率：当前概率依赖实际接收位置和法线，近似复用会改变分布。
- 不以“先粗判走哪边”声称可省掉另一边度量：后续 remapped random 与精确 PDF 仍需要真实分支概率。
- 不在本轮调整 SAOH、旋转逻辑树或改变叶分组。这些会改变层级的聚合指标与概率，需要独立的质量研究；现有 builder 已有 SAOH 和深度成本折中。
- 不因所有灯仍有非零概率就声称质量不变；保留支持域只保证基本正确性，不能保证原有方差。
- 不把按接收点排序、subgroup broadcast、更多 shared memory 自动视为收益。相同地址读取可能已被缓存/合并，更多调度也有成本。

建议以现有 CPU tree 输出和捕获的查询建立 GPU replay：同一 `point/normal/u` 对照最终 emitter、每级分支、remapped 值及正反向 PDF。表示/调度变化以离散结果一致、浮点尽可能逐位一致为目标，专门覆盖靠近分支概率的随机数、零距离、双面灯、零法线、坐标重定位和极端功率。

性能顺序是：先验证纯 hint SER 的收益假设，再比较编译分支/叶记录，最后尝试 treelet 或显式分类。每项都测整个选灯阶段和整帧，不将函数采样百分比直接当作可回收毫秒。当前资料还没有给出可承诺的提升幅度。

## 2. 让翻译层编译阴影交互，而不只是通用材质

### 已具备的条件

[SurfaceDefinition 规范](C:/WorkSpace/prime/docs/区块簇场景翻译架构.md:147) 已明确 positive/negative side、介质端点、覆盖层与 substrate，并统一 winding。同介质内部面已删除，玻璃 A/B 已归并为一个 boundary。这些已有优化不再作为建议。

但 [shadow_nonopaque.anyhit](C:/WorkSpace/prime/shaders/entry/hit/shadow_nonopaque.anyhit.slang:55) 仍在每次候选处理时解析通用 relation/recipe、获取参考 UV/tint/颜色、判断 stained glass、计算消光，并可能再次解析另一侧介质。在本次采样中，opacity、candidate surface、参考 base color 与 candidate normal 都有可见成本。

### 建议的数据流

`SurfaceDefinition + 规范纹理 generation + tint/reference UV → 去重 ShadowInteraction → any-hit`

生产者在资源/场景发布时，对与射线无关的部分做精确求值。记录表达离散交互类型、覆盖规则、两侧介质身份和规范消光结果。初始范围限定为参数已知的静态 SINGLE/BOUNDARY；overlay、bilateral、动态 tint 等仍沿明确的通用类型处理，不能静默按普通玻璃解释。

这不是扩展 MaterialId 的 key，也不是 `MediumId → extinction` 表：相同身份不意味着连续参数可以忽略 tint、参考 UV 或动画。宜使用去重的 surface companion，引用键必须包含实际影响派生结果的输入。保持 PrimitiveRecord 32 B，避免每三角形复制两套光学参数。

具体可以前移：参考颜色采样、stained/clear 分类、两侧 shadow extinction 的计算与 canonicalization、明确的介质方向关系。必须保留逐候选 coverage/玻璃装饰边判断；这些依赖命中 UV，不能预设为常量。

动画更新必须与规范页面一起生成/发布派生数据；资源 reload、新 generation、tint 变化不能留下旧 extinction。GPU 构建若能复用同一 Slang 数学，较容易保持过滤、运算顺序和已有 canonicalization；不能用 CPU 另一套近似公式替代。先保持输出 f32，不借此新增量化。

普通 solid 只需要进入/离开符号时，还可研究以硬件 front/back 加已知 winding 代替完整法线求值；thin-walled 仍需要角度。负行列式变换、instance facing flags、极端掠射及原有符号规则必须先证明等价，这只是候选，不是已经成立的简化。

这条路线主要借鉴 PBRT/Cycles 的按消费类型拆分，以及 Prime 自身已经进步的翻译 IR；没有声称参考项目存在可直接移植的同名完整方案。

### 成本与验收

以新增 companion 带宽和更新成本，换每次候选的多级读取、纹理查询及重复计算。先量出水、普通玻璃、染色玻璃、cutout、overlay 各类候选次数，防止专门优化了很少触发的类型。

验证输入纹理动画、tint、两侧不同介质、薄片/实体、clear glass 装饰边、seamless 选项与两种透明 NEE 模式。比较既有 transmittance、hit distance、source/target 拒绝和介质状态的可执行结果。现有 OMM、精确端点身份、BLAS f32 顶点与硬件重心坐标全部保留。

## 3. 从分阶段函数改为按工作类型组织数据流

当前完整模式已是 Wavefront，默认录制 `4K+9=57` 个追踪阶段，空队列为零宽度间接调用。路径/阶段暂存/索引容量约为每内部像素 `96+280+36=412 B`，不是每跳读写 412 B 的测量值。

下一步应研究整个 bounce 的执行图：

`surface trace → 分类/材质求值 → ShadowRequest 与 continuation → 可见性追踪/结果归并`

[PBRT 的 ShadowRayWorkItem](C:/WorkSpace/_ref/pbrt-v4/src/pbrt/wavefront/workitems.soa:77) 将阴影请求独立；[MaterialEvalWorkItem](C:/WorkSpace/_ref/pbrt-v4/src/pbrt/wavefront/workitems.soa:156) 按具体材质组织任务。[Cycles](C:/WorkSpace/_ref/blender/intern/cycles/integrator/path_trace_work_gpu.cpp:529) 根据 shader 分类和稀疏程度整理 active path。应学习这个工作分配边界，而不是照搬其 CPU queue readback 或 C++ 对象布局。

联合方案包括：

- 少量 exact topology 队列，在独立 compute 入口中完成实际需要的 BSDF 求值与 continuation 生成；不能对连续 roughness 阈值裁掉非零 lobe。
- 直接光在适当的求值阶段生成带权请求。shadow 阶段只拥有物理线段、精确 source/target、起始介质、输出槽等必要数据，不跨调用保留完整表面和通用材质。
- 太阳/面积光结果用明确槽位归并，避免为了并发引入不确定的浮点 atomic 累加顺序；两个透明 guide 的所有权仍独立。
- 以阶段最后使用为准重新安排 surface 与选灯查询状态生命周期，再决定 SoA/AoSoA、紧凑 active state 和 alias；只改变索引队列并不会自动让状态访问连续。
- 没有追踪工作的 entry 采用 compute 是此设计的结果，不预设把 raygen 改成 compute 就有收益。

重要反例：当前是先 shadow、可见后才做部分 BSDF 求值。提前计算权重会给被遮挡的光样本增加无效 BSDF 工作；请求写回、额外 dispatch、队列分类也会增加成本。因此必须比较完整 bounce，包括遮挡率高/低、材质同质/混杂和稀疏尾部。不能用 live state 从 208 B 降到某个数字作为唯一验收。

它需要更新现有阶段 ABI、生命周期和编译闭包设计；不是恢复宽 raygen/尾部 megakernel。每个拓扑入口只看实际需要的数学与数据，OpenPBR 公式、RNG 地址、事件及 guide 输出保持合同。现有 SER/OMM 和精确几何查询可继续使用。

## 4. 通过辐射缓存减少路径尾部

参考 [SHaRC Integration](C:/WorkSpace/_ref/SHARC/docs/Integration.md) 与 [MCVR 的实际调用](C:/WorkSpace/_ref/MCVR/src/shader/world/ray_tracing/internal/vanilla-pt/world/world.rgen:648)：少量路径更新世界空间缓存，resolve 历史，渲染路径在合适命中处查询并终止。

它有机会同时减少 trace、选灯、阴影和 scatter，作用范围大于只优化某个 1% 热点。Prime 已有 MediumId、表面身份和场景修订，适合明确构造缓存有效性规则。缓存 owner、accepted frame、abandon、rebase 与 generation 必须进入设计，不能只给命中 shader 加一个 lookup。

建议先限定为非首表面的粗糙反射尾部，保留镜面/折射链与重建 guide 的独立职责。缓存的辐射语义、方向性及 BSDF 因子必须写清，避免重复乘 albedo 或把方向辐射当作 irradiance。不能为便于缓存把 OpenPBR 表面改为 Lambert。

直接复用邻近位置/历史辐射并终止路径会引入偏差。薄墙漏光、移动/昼夜变化、发光体动画、镜面、玻璃和焦散都需要单独验证。因此适合显式的缓存实时模式；不作为现有完整模式的数学等价实现。缓存历史不是现有 DLSS 历史，可以相互影响，必须共同评估运动质量。

SHaRC 文档示例约 4% 更新路径只是起点，不是 Prime 的推荐常量。其基础三数组按 `2^22*(8+16+16)` 为 160 MiB，额外锁、方向编码或其他资源另计。SDK 自带的 fp16 表示也不自动满足 Prime 的精度合同。

收益判据：节省的路径尾部总时间必须超过 sparse update、resolve、hash/query 的总时间，并在同样的输出误差目标下仍然成立。缓存暖机、视角突变与编辑后恢复同样属于成本。

## 5. 移动场景：增量依赖图，而非孤立的更快容器

本次静止 CSV 不能判断以下方向的收益，保留为第二组调查。

- **section 事实 → cluster 翻译**：[VanillaClusterCompiler](C:/WorkSpace/prime/src/client/java/dev/prime/render/scene/vanilla/VanillaClusterCompiler.java) 对 cluster snapshot 的 section 重新编译。可缓存不可变 section 事实，并用 dirty/halo/resource generation 依赖图决定重编译范围，仍保持完整 cluster 原子发布。biome tint、fluid、模型邻接、mod 动态依赖必须完整失效。Voxy 的 [RenderGenerationService](C:/WorkSpace/_ref/voxy/src/main/java/me/cortex/voxy/client/core/rendering/building/RenderGenerationService.java) 可参考任务粒度和 worker scratch；其中 render cache 还是 TODO，不把它当现成实现。
- **几何修订 → 灯光修订**：[TerrainScene](C:/WorkSpace/prime/src/client/java/dev/prime/render/vulkan/terrain/TerrainScene.java:209) 在静态内容改变或 rebase 时重建世界灯光树。建立独立且可证明的灯光输入 revision，只有精确叶输入/映射变化才刷新对应派生结构；与方向 1 的编译树发布一起设计。
- **场景修订 → 绑定发布**：[TraceBackend](C:/WorkSpace/prime/src/client/java/dev/prime/render/vulkan/TraceBackend.java:430) 的 SceneBindings 重建包括 pool/set。可将稳定纹理/材质和旋转 TLAS/frame 绑定拆开，以 timeline 退休后复用池。参考 [LuisaCompute device](C:/WorkSpace/_ref/LuisaCompute/src/backends/vk/device.cpp:400) 与 [stream reset](C:/WorkSpace/_ref/LuisaCompute/src/backends/vk/stream.cpp:62)。这里并不建议照搬其线程/锁模型。
- **部分实例更新 → PTLAS**：[vk_partitioned_tlas](C:/WorkSpace/_ref/vk_partitioned_tlas/README.md) 展示分区增量维护；Prime 已有同实例数的 TLAS UPDATE 和动态原型复用，新增价值只能是减少整表写入/整 TLAS 更新。需先查询设备与驱动的 NV 扩展支持，不能由 RTX 4090 型号或当前 enabled extensions 推断。动态全局分区还可能降低追踪效率。

`DynamicMeshBuilder` 的逐顶点 `new Vertex` 是明确的分配候选，但 primitive 数组/scratch 复用只算配套。没有 JFR 和移动时间线，不把它上升为静止低帧率根因。

## 暂不作为主线的方案

| 方案 | 原因 |
| --- | --- |
| 再引入 Wavefront、SER、OMM、SAH、TLAS refit | 当前已有；要评估现有效果与适用范围 |
| 简单降低反弹数、放大 epsilon、截断身份、全局 FP16、裁 BSDF lobe | 改变行为或违反现有契约，不是本次目标 |
| 只减少 RT 调用活跃状态 | 有改进空间，但本次 dependency-attributed samples 不支持独占最高优先级 |
| ReSTIR 类方法 | 用户明确排除；不再作为候选 |
| RTXDI ReSTIR GI 原样用于完整材质 | 其文档的次级 radiance 表示采用 Lambertian 化假设，不能当任意 OpenPBR 的等价替代 |
| 合并 guide 与照明路径 | Prime 已共享部分状态，并有不同的分支规则；只有证明同一查询可复用时才成立，不能因方向相近合并 |
| 更激进的 voxel/geometry LOD | 需要新的场景几何语义与重建质量合同，当前不能替代权威 BLAS 几何 |

## 最小验证路线

1. 固定本次静止场景，补齐内部 extent、各 pass GPU 毫秒，以及 landing/secondary 各 bounce 的 active path、实际 shadow 数、遮挡率和 any-hit 类型计数。选择采样而非每候选全量 atomic，避免诊断自身改变瓶颈。
2. 对同一逻辑灯光树建立查询 replay，验证纯 hint SER、编译分支/叶记录以及 treelet 的完整成本与原分支/PDF 一致性。
3. 用翻译期 ShadowInteraction 对选定 SINGLE/BOUNDARY 类型做行为对照，验证动画发布后再比较整个阴影阶段。
4. 以 1/2 形成的新数据为基础比较工作图：当前流水线与 typed material/shadow request 流水线。所有时间包含准备、分类、barrier 和归并。
5. SHaRC 独立衡量精度/时效性；移动场景另抓时间线/JFR，验证增量更新方向。新增共享可变缓存系统在实施前需按 AGENTS.md 审查所有者与线程/锁边界；本调查不引入这些系统。
