# 阶段 2 编码精度初始预算

阶段 2 的持续测量、自动决策和阶段 3 准入状态见
[阶段 3 准入账本](阶段3准入账本.md)。初始预算是迁移起点，不替代真实样本和误差上界。

## 1. 状态与目的

本文是阶段 2 的**解析估算与迁移账本**，不是最终 encoding 批准。它回答两个问题：

1. 在场景统计、图像差分和完整 GPU profile 尚未收集前，哪些表示已经有足够依据可以作为迁移起点；
2. 哪些字段不能因“通常够用”而先压窄，必须保留保守表示并等待误差和性能数据。

最终语义仍以[渲染核心数据 IR](渲染核心数据IR.md)为准，几何不可放宽项仍以
[GPU 几何追踪精度契约](GPU几何追踪精度契约.md)为准。本文中的误差目标是用来设计测试和
比较候选的初始预算；只有写入 `shaders/renderer-data.json` 且通过对应门禁的 encoding 才是
生产合同。

2026-08-31 已开始第一批迁移：精确 `MediumId` 已贯穿 CPU 翻译、GPU 场景 ABI、实时/离线
wavefront 和 shadow。primitive identity carrier 已把 `MaterialId:u16` 与 `MediumId:u16` 合并进原有
32-bit word；path/payload 中尚未适合合并的 ID 仍保持具名 `u32` lane，但逻辑值域都受 u16 上限约束。
连续 extinction 暂时保持原有路径内联表示，最终参数表与窄化仍等待本文件第 6 节的数据。

## 2. 估算边界

本轮采用以下保守上界：

- 最大合法纹理或页面维度按 32,768 texel 估算；现有 texture record 的坐标域是 unsigned 16-bit；
- 最大路径深度按生产 ABI 的 128 次 scatter 估算；
- volume stack 按当前最大 2 层估算；
- motion/重投影的候选目标为最坏不超过 `1/256` pixel，UV 采样候选目标为最坏不超过
  `1/64` texel；这两个值尚需 RR/FG 图像门禁确认；
- 对仍可见的透射，先以 `T >= 1e-4`、相对 transmittance 误差 `<= 1e-3` 估算 extinction；
- 对 Russian roulette，先以单次 survival probability 绝对误差 `<= 1e-4` 估算累计状态。

这些目标不是以视觉阈值替代数学行为。TIR、命中、自交、身份、拓扑和离散事件没有可交换的
普通误差预算。

### 3.2 耦合数据与 table-first 物理布局

精度需求不意味着每个 triangle 都要重复保存完整材质状态。当前样本的 unique BLAS triangle 已达
约 2,084 万，而 Texture/Medium/材质 binding 仍在 `u16` 资源域内；阶段 2 因而采用以下布局原则：

```text
MaterialId u16
  -> TextureId u16
  -> MediumId u16
  -> MaterialRecipe / exact source codes / channel availability
  -> emission、coverage、animation 与规范 texture-record references

Triangle
  -> exact orientation / geometry-varying UV or texel transform / relation
  -> MaterialId u16
  -> geometry-varying tint-field reference or local samples
```

`TextureId` 是材质去重键的首要组成，但不能单独代替 `MaterialId`：同一纹理仍可能在 medium、
recipe、coverage 或离散 source facts 上具有不同语义。目标 key 由 `TextureId` 加这些确实改变材质
行为的离散事实组成；世界位置直接来自提交给 BLAS/TLAS 的几何与命中，不在 triangle record 中
重复保存。对常规 terrain，`MaterialId + exact orientation + world position + continuous tint` 应足以
推出绝大多数纹理、法线、材质和 OMM 查询；例外必须在 schema 中具名，而不是为所有 triangle
预留一份完整状态。

- material、texture、medium、source code 和静态控制按 generation 去重进表；不得在每个 triangle
  复制 f32 roughness、IOR、extinction、page address 或完整 secondary material record；
- surface relation 引用 primary/secondary `MaterialId`，emitter table 以 `EmitterId u32` 引用同一
  material record；身份 carrier 不复制材质参数；
- tint 与 albedo binding 保持语义耦合，但 biome/顶点变化属于 geometry-varying field；triangle
  只保存能够定位其连续 RGBA16F samples 的最窄无损引用，不能退化为面平均材质 variant；
- derived roughness、IOR 和其他计算值从 source code/table 在消费寄存器中展开为 f32。若热路径
  测量证明值得缓存，只能每 material record 保存一次，不能按 triangle 重复；
- `MaterialId`、`TextureId`、OMM pattern、emission distribution 和其他可由稳定内容键唯一化的
  资源使用 renderer-generation 全局 dense table；section/cluster 不建立会复制内容的 local palette；
- GPU 热路径由 `MaterialId` 一跳直接寻址固定 schema 的 material table，但不要求 shader 一次加载
  或长期保留完整 `MaterialRecord`。generated accessor 必须允许各 wavefront 阶段在消费点窄加载
  所需字段并立即结束其活跃期；需要多数事实的阶段仍保留合并加载能力。page/origin/extent、recipe、
  availability 和常用 source codes 可采用 AoS、SoA 或混合布局，以实测 load 数、合并访问、寄存器
  压力和跨阶段状态大小决定；冷数据最多进行一次由 exact availability 控制的 companion lookup；
- 禁止用变长 record、链表、hash probing 或多级指针追逐换取更高压缩率。triangle 记录保持固定宽，
  shader 的访问次数与分支由 schema 固定；
- ordinary terrain BLAS 按实际 cluster geometry 唯一拥有，不为随机世界中几乎不存在的整 BLAS
  重复建立昂贵全局去重；只有已有明确稳定复用键的纹理体素/模板 geometry 可共享；
- schema 必须显式表达所有关联并在 generation 发布前验证 u16/u32 上限。

该原则允许先压掉数量级最大的重复状态，再讨论单个连续值是否值得进一步有损压缩。

## 4. 解析依据

### 4.1 exact identity 与 source code

`TextureId` 与 `MediumId` 的目标物理身份域均为 exact `u16`。vacuum、missing、invalid 等状态不得
通过连续值 sentinel 推断，也不得让迁移期 `u32` carrier 暗示更大的生产 namespace。
因此第一轮迁移应优先引入：

- `TextureId u16` 和 `MediumId u16`，其中 medium 0 明确表示 vacuum；
- `HistoryValidity`、hit kind、front/back、thin/solid 和 branch event 的独立 exact bits；
- Fresnel、roughness、normal、AO、emission 和 LabPBR 类别通道的原始 `u8` code；
- 只由 generated accessor 解释的 typed control word。

`MediumId` 与 texture/material binding 近似一一对应，不能因 tint、实例或连续参数组合复制身份。
各类 catalog 都必须在 generation 发布前验证 `u16` 容量。primitive 已将 MaterialId/MediumId 共享为
高/低两个 16-bit field；path、payload 等独立 `u32` lane 是迁移布局，不表示更大的身份域。是否继续
合并其他 carrier 只由生命周期与布局 benchmark 决定。

### 4.2 UV 与页面坐标

目标设备的合法 texture extent 不超过 32,768；Minecraft/Fabric 生产来源最终都映射到该有限
纹理域。当前 `UQ0.16` 对 32,768 以内 power-of-two texel boundary 逐点精确，端点 1 使用
`0xffff` 的明确编码。插值与导数在解码后使用 f32，但不为不存在的无限精度 authored UV 建立
另一套持久化 ABI。若未来输入超出规范纹理域，应在资源边界失败，而不是扩大每 triangle UV。

材质参考点也不应借“任意 UV”长期保存两个 f32；其权威事实是 texture-local integer texel/区域
身份，应移入 material/texture table，再在采样寄存器中生成坐标。

页面 origin/extent 不参与插值，只需精确表达整数坐标。现有 16-bit/axis 足够，但页面构建器必须在
分配或上传前硬性拒绝超过 65,535 的值。

### 4.3 linear Rec.2020 base color

binary16 有 10 个显式 fraction bits、11-bit significand。对 `[0,1]` 值，单次 round-to-nearest 的
最大绝对误差为：

```text
2^-12 = 0.000244140625
```

linear sRGB → linear Rec.2020 的当前矩阵系数非负且每行和约为 1，因此合法 reflectance 仍在
`[0,1]`。这使 `RGBA16F` 成为 base-color canonical page 的合理起点：

- 误差小于 `0.5/255`，所以 mip-0 alpha 的任一原始 u8 code 经过 FP16 后仍可由
  `round(alpha * 255)` 无碰撞恢复；
- bilinear 的凸组合不会放大四个 texel 的最大输入绝对误差；
- 每个 mip 必须从高精度线性源独立生成后只量化一次，禁止逐级从 FP16 mip 继续累计生成；
- OMM/cutout 的权威 mip-0 coverage 仍由 source-faithful code 构建，不能让过滤后的 color alpha
  重新定义可见性。

首版 canonical base-color encoding 将 A lane 保存为 `0..255` 的整数-valued binary16，而不是先归一化再
量化；256 个 source coverage code 因而逐值精确，读取/采样后再除以 255。RGB binary16 与下述
tint 混合路径的组合解析误差目标仍为 `1/2048` absolute reflectance。此门限只批准
source-derived `[0,1]` reflectance/tint sample，不得外推到 radiance 或 transport。

这还不是对 `R11G11B10F`、10-bit UNORM、BC6H/BC7 或共享指数的批准。它们的暗部、跨通道或
block error 需要真实纹理和图像门禁。

#### tint 不能在 Rec.2020 中直接逐通道相乘

Minecraft tint 当前是在 linear sRGB 中做逐通道 modulation，再转换到 Rec.2020。设色域矩阵为
`M`，通常有：

```text
M * (base * tint) != (M * base) * (M * tint)
```

因此迁移不能把 base 与 tint 各自转到 Rec.2020 后直接相乘。tint 通常来自资源包可替换的
colormap、biome blend 或 mod provider，并在边界形成连续过渡；它是与 albedo binding 关联的连续
颜色场，不是离散材质身份。阶段 2 锁定以下合同：

1. 捕获的四顶点 tint、实例 tint 和可采样 tint 均保留 RGBA，进入 GPU 前以 `RGBA16F` 表示；
2. 插值在声明的线性颜色域进行，不得先平均为单个面颜色；alpha 与 RGB 一同保留，但使用独立
   coverage/modulation accessor；
3. material adapter 必须执行与 `M * (base * tint)` 数学等价的转换。可以测量后选择 source-linear
   modulation、等价 operator 或其他组织，但不能把两个 Rec.2020 RGB 直接逐通道相乘；
4. `TintId` 如仍存在，只能是连续 tint sample/field 的无损地址，不再代表一个 RGB8 离散身份，
   也不能成为 16-bit 精度替代；
5. 非均匀 tint 在证明合并后仍保持同一插值场以前，不得参与会改变顶点/采样域的矩形合并。

RTX 4090 的固定 Vanilla 与 SPBR-21 世界样本已经覆盖普通图元、surface relation、area-light
emitter 和实例 tint：约 312–314 个实际纹理产生 1880–1887 个 `(TextureId,tint)`，逐 pair
预合成会把已用 mip texel 放大到 6.08–6.09 倍，单是 `RGBA16F` 约 124 MiB；SPBR 样本还包含
132 个 animated pair。扩展样本的膨胀达到 12.70 倍。因此阶段 2 排除全量预合成 variant；这些
统计只决定存储组织，不允许把连续 tint 降为离散 RGB8、面平均值或省略色域转换。

### 4.4 motion 与 depth

若 signed normalized motion 的有效范围先按 `[-1,1]` 估算，b-bit 固定点的最大像素误差约为：

```text
error_pixel ~= extent / 2^b
```

在 32,768 像素上满足 `1/256 pixel` 需要约 23 bits/component；motion 超出 `[-1,1]` 时还需要更多
范围。FP16 的误差随 motion 幅度增长，在 normalized motion 接近 1 时最大误差可达 16 pixels，
因此 `RG16F` 不能作为全域精度合同。阶段 2 的 canonical `VisibleMotionUv` 与 specular/virtual
motion 先使用 `RG32F`，并由独立 validity bit 表达 camera cut、miss 或无 history。

当前 RR、NRD/FSR 和 Streamline adapter 已由同一精确 history bit 门控；reset 帧不再靠 sample
index、矩阵异常或非有限 motion 推断。Streamline 在 backend 覆盖 scratch 前读取真实可见表面的
`R32F LinearViewZ`，相机运动在 adapter 中以 f32 矩阵重建。动态物体不再把
previous-minus-current 位移量化进 `RGBA16F transportMetadata`：普通/RR 路径直接复用既有
`RGBA32F primaryPosition`，NRD 路径直接复用既有 `RGBA32F displayPosition`，两者保存运动物体的
上一帧位置，因此没有新增图像、显存或 delta 量化。`ReconstructionControl` bit 5 逐位声明物体
运动。RR 的运动中透射界面没有独立可见历史位置，Streamline 对这一小类明确写 invalid motion，
不使用 virtual primary 伪造结果；NRD 的 display position 可完整覆盖该类。

动态测量器仍保留 binary16 delta 候选的位移、round-trip 和有效视锥投影误差统计，便于评估其他
窄编码。首批猪实体样本覆盖 3,517,920 个顶点，其中 1,917,833 个发生运动，最大位移
`0.508535 blocks`，最小非零位移 `4.768e-7 blocks`，binary16 最大 component/vector 误差分别约
`1.1444e-4/1.2778e-4 blocks`。这批数据不再作为 Streamline 编码准入依据，因为零额外成本的
f32 history producer 已消除该有损转换。

FP16 linear depth 在 2,048 blocks 附近的 ULP 已约为 2 blocks。若在 32,768 blocks 仍要求
`1/64 block`，需要约 21 bits 的有效相对精度，标准格式中应直接使用 `R32F`。RR linear view-Z、
FG reversed depth 和 NRD 的 backend depth 是不同 semantic；它们可以都用 32-bit，但不能共用名称
或 sentinel。

### 4.5 position 与 normal

GPU position 先由 CPU double/整数绝对坐标转换为 camera-relative f32。以 2,048-block camera-relative
范围估算，f32 spacing 约 `1/4096 block`；FP16 spacing 则约 2 blocks。提交给 BLAS 的顶点、硬件
重心和由其重建的位置继续服从几何精度契约。

对参与 TIR、Fresnel、BSDF hemisphere 或可见性判定的 normal，不存在一个有限的非零角误差能对
所有临界输入保证分支不变：合法输入可以任意接近临界角。因此这里的最低要求不是“oct16 大概有
多少度误差”，而是保留当前权威 f32 三角形导出的 f32 normal 结果。任意有损 world-normal encoding
都必须显式排除分支消费，或接受完整临界输入门禁。

当前非几何方向已经分成三个用途专属合同，而不是一个待选的通用 `SNORM16x3`：

- `primaryAreaDirection` 是从 surface 指向本次主要 area-light sample 的方向，只用于构造 NRD
  effective SH moment；跨 realtime wavefront area queue 时使用一个 32-bit oct-SNORM16x2 word；
- diffuse/specular direction 是每像素辐射方向 moment，只供 NRD SH 输入和 composite 使用，当前
  保存在 `RGBA16F` direction images；
- light-tree emission direction 是每 node 的保守 cone/lobe bound，使用专用 32-bit 编码；axis 与
  cone 量化误差已经扩入 bound，不能改成普通向量后丢失保守性。

`previousLightNormal` 是参与 area-light/MIS 计算的 receiver normal，tangent 是 shading frame；二者
都不属于上述可损 reconstruction direction。现阶段只需审计三个专用编码的角度/能量合同，不再
保留“是否使用 SNORM16x3”的开放决策。

### 4.6 medium identity、IOR 与 extinction

阶段 2 首先修复结构，而不是先压参数：

```text
PathMedium = { MediumId exact, parameter reference }
MediumParameters = { extinction f32x3, IOR source code/table }
```

当前 dielectric IOR 来自 8-bit Fresnel code 或 water 常量。保持 code/table identity 后，计算时再
解码为 f32，比在每个 path 中存一份匿名 IOR 更准确也更容易比较。当前 F0 合法范围 `[0.02,0.17]`
对应 IOR 约 `[1.3294, 2.4032]`。

Beer-Lambert 有：

```text
T = exp(-sigma * L)
relative_error(T) ~= L * error(sigma)
```

当 `T >= 1e-4` 时 optical depth 最大约 9.21。若相对 T 误差预算为 `1e-3`，sigma 的相对误差需约
`<= 1.1e-4`，即至少约 13 个 fraction bits，此外还要覆盖 zero 和动态范围。FP16 只有 10 个显式
fraction bits，最坏会把该误差放大到约 `4.5e-3`；固定 16-bit 对接近零的 extinction 更差。

所以起始 medium table 使用 `float32x3`。后续可评估带 zero code 的 log/floating encoding，但必须
先取得最小非零 extinction、可见 optical-depth 分布和最长介质段；不能对连续 filtered color 假设
一个不存在的最小正值。medium matching 始终只比较 `MediumId`。

### 4.7 etaScale、roughness、ray cone 与累计输运

迁移前 realtime `etaScale` 每次跨 dispatch 写成 FP16。binary16 单次相对 half-ULP 最坏约
`4.88e-4`。若按 128 次存取、survival 误差 `1e-4` 反推，每次允许的相对误差约为：

```text
2 * 1e-4 / 128 = 1.56e-6
```

这需要约 20 个 fraction bits，FP16 明显不足，f32 的 23 fraction bits 是合理起点。可以进一步
验证 eta product 是否能由 exact initial/current `MediumId` 与 IOR code 直接重建；若严格 telescoping，
该累计字段可能被结构性删除，但在证明前不应依赖这一点。

2026-08-31 已将 realtime transport record 的 `previousLightNormal.w` 明确为 `etaScale` 的 f32
carrier，不增加 144-byte path stride；原 path-control bits 8–23 清零并作为保留域。生成 ABI 固定
offset 108，GPU 性质测试覆盖正 subnormal、最大有限值和随机指数域的逐位往返，实际 RR 多 pass
运行通过。该迁移不批准未来压窄；若要删除累计字段，仍需先证明由介质/IOR 身份重建严格等价。

roughness 的权威 source code 只需 8 bits，delta/non-delta topology 使用独立 exact bit。纹理过滤、
normal-distribution 合成和 BSDF 计算可在寄存器中展开为 f32，但 scene/material/triangle record 不
持久化高于源艺术精度的派生 roughness；跨阶段需要保存时使用能够保持 source step 与过滤结果的
最窄格式。throughput、radiance 和 PDF 继续保留 f32；它们是累计 transport 状态，不属于派生材质
参数，候选 encoding 必须按最大 bounce 累计，而不是只测一次 pack/unpack。

当前 ray cone 不是沿 path 累积的 transport 状态：CPU 根据投影和 render extent 生成 primary
pixel-cone spread，命中时才以 f32 的 distance、UV density 和 incidence 推导 LOD。Java 现传递
`RayConeParameters(width, mipBias)` 的原始 f32 语义，只在 Vulkan push writer 打包为 binary16x2。
构造器以独立 f32 公式比较打包前后的最终 unclamped LOD，并拒绝误差超过 `1/512 mip`、下溢为零
或上溢的输入。五档生产 quality 的最坏实际误差小于该上限；derived LOD 仍以 f32 计算和 clamp。
这项收缩不依赖世界分布，也不把 half2 暴露给上层 API。

## 5. 可立即开始的迁移顺序

在没有场景分布数据时，仍可安全推进以下工作：

1. **先迁移 exact facts**：把 `TextureId`/`MediumId` 的逻辑域锁定为 `u16`，并引入 validity、
   topology/event 和 source-code typed accessor；不改变连续参数数值。
2. **medium 身份先精确化**：path/shadow 携带 exact ID，extinction 先保持 f32 inline；先证明行为，
   再比较 generation-stable table lookup 与 inline 参数的 GPU 成本。
3. **建立 provisional canonical color catalog**：base color 使用 linear Rec.2020 `RGBA16F` 双路径
   生成，mip 从高精度源一次量化；tint 以绑定到 albedo 的 `RGBA16F` 连续 field 保留四顶点/采样
   过渡，混合执行显式色域转换；保留旧路径做数值/图像差分。
4. **先迁移 NVIDIA 坐标，不压数据**：top-left producer 直接写 `RG32F` motion、`R32F` depth；RR 与
   Streamline 共用 semantic，NRD/FSR adapter 承担转换。
5. **引入 phase-specific typed views**：world normal、position、radiance、roughness 等仍使用当前
   f32/现有 backend 格式，只消除通道猜测和 sentinel。
6. **收集数据后再窄化**：所有窄化均作为独立合同 diff，不与坐标、颜色或 owner 迁移混在同一
   行为变更中。

### 5.1 起始 profile 的显存量级

- RR motion 从 `RG16F` 改为共享的 canonical `RG32F`，单独看 RR 增加 4 B/render-pixel，即 4K
  约 31.6 MiB；FG 开启时若同时删除现有独立 `RG32F` Streamline motion，则两份合计反而减少
  4 B/render-pixel。是否常驻应按 backend lifetime 决定。
- linear Rec.2020 `RGBA16F` color page 相对 RGBA8 source 增加 4 B/texel。它是正确采样所需的
  renderer-owned catalog 成本，后续是否能用 32-bit/block encoding 回收必须由纹理门禁决定。
- 当前每个 path 的两层 medium 参数占 32 B。若两个逻辑 `MediumId u16` 可引用 generation-stable f32
  参数表，persistent path 理论上可减少 24 B；这项收益需扣除 table load/cache，并留到记录布局
  benchmark 后兑现。

### 5.2 第一批迁移的实际布局

第一批实现选择先消除身份歧义，不把参数表、stride 优化和连续值窄化混入同一行为变更：

- cluster 翻译为每个 solid transmissive surface 建立 invocation-local catalog。water 使用固定语义，
  block medium 优先使用显式 family，否则使用稳定 `TextureId`，并保留完整 tint；thin-walled 与
  non-transmissive surface 的 ID 固定为 0；
- `TerrainScene` 当前在上传边界把 cluster-local ID 映射到迁移期 renderer-lifetime `u32`
  carrier。0 是 vacuum，water 是 1，其他 ID 单调分配且 renderer 生命周期内不复用；所有值在超过
  `u16` 容量前失败；
- `TerrainScene` 另有 renderer-lifetime dense `MaterialId` registry。0 保留给 dynamic/baked，其他
  exact key 单调分配且不复用；cluster-local resolution cache 仅消除重复 key lookup，不形成局部表；
- `PrimitiveRecord` 的原保留 word（offset 16）现承载高 16-bit `MaterialId` 与低 16-bit `MediumId`，
  仍为 32 B；`BOUNDARY` relation 的 adjacent identity word 使用同一布局，其他 relation 不增长；
- `TracePayload` 与 `SurfaceInteraction` 使用既有保留 lane 携带 current/adjacent ID，仍分别为
  112 B；实时 surface record 仍为 112 B；
- 两层 wavefront medium lane 以 `float32x3 extinction + u32 MediumId` 保存。IOR 不再作为匿名 f32
  跨 dispatch 存储，而是保存精确 8-bit Fresnel source code 或 water code，并在消费处用生产公式
  重建；实时与离线 path record 均保持 144 B；
- guide 控制与 IOR source code 虽暂时共用一个 control word，但只能通过具名 mask 合并；guide
  分叉不得整字覆盖 medium encoding；
- shadow payload 携带两项起点 `MediumId`，any-hit 只按 ID 匹配边界，不再从 extinction epsilon
  反推身份。shadow 的连续 extinction 仍沿用既有 FP16 round-trip 参与数值积分，后续按
  Beer-Lambert 误差数据单独迁移；
- offline surface scratch 从 100 B 增至 108 B 以保存两个 ID；其 112 B stage record、Light Select
  尾部和队列布局保持不变。

门禁覆盖 local→renderer remap、两类 ID 不复用/u16 溢出、primary/secondary/boundary 的 identity
packing、cluster-local key resolution 去重、回放格式、SPIR-V payload shape、全部 8-bit IOR code、
跨 dispatch bit-exact extinction、guide-control 合并和 shadow ID match/mismatch。Shader 目前只从
primitive identity word 窄读 MediumId；MaterialId 已可取出但尚未连接 GPU material table。该切片
没有批准 material/medium 参数表，也没有批准 extinction、IOR 计算值或其他 transport 连续字段的
有损 encoding。

## 6. 阶段 2 编码定稿前必须取得的数据

| 数据 | 决定什么 |

| texture/page 最大尺寸、mip、总 texel、格式和动画更新量 | RGBA16F catalog 成本及压缩候选 |
| `(TextureId, tint)` 唯一数、频率和 variant 膨胀率 | 已取得：扩展样本最高 12.70×；仅排除全量预合成 variant，连续 tint field 仍为 RGBA16F |
| `TextureId`/`MediumId` 高水位、有效数、reload 空洞率 | 已锁定 u16；后续数据验证容量失败路径和 generation 行为，不再决定是否压窄 |
| `MaterialId` exact key、驻留引用和动态/烘焙例外 | 已验证：705 key / 31,425,734 驻留候选引用 / 64,830 个剩余 ID；registry 与独立 oracle 一致，支持 renderer-global dense u16 table |
| extinction 各通道最小非零、分位数、optical depth 与 segment length | f32、log 或自定义 float 位数 |
| etaScale 范围、每路径量化次数和 survival 差分 | f32、重建式表示或其他编码 |
| motion 像素幅度、重投影误差、camera cut/越屏比例 | RG32F 是否能按范围拆成更窄表示 |
