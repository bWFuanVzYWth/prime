# Prime 渲染数据标准化调查报告

> 调查基线：本地 `26.2` 分支，提交 `51a4f00c`（2026-08-31）。  
> 本文是现状审查和后续统一工作的设计输入，不改变现有渲染行为或 ABI。

## 1. 结论

Streamline 接入暴露的问题属实，但根因不只是 Streamline 所需的坐标或图像格式与 Prime 不同。
Prime 已经有一组总体合理的内部约定，例如线性 Rec.2020 工作色域、camera-relative 世界坐标、
以当前 f32 形式保守保存的追踪几何、稳定 `TextureId` 和生成式 Shader ABI；真正缺失的是覆盖
所有常用数据、可由类型和工具执行的渲染核心 IR。

当前 `VulkanImage` 只记录句柄、`VkFormat`、usage、尺寸和 mip，`VulkanBuffer` 只记录句柄、地址
和字节数。它们都不能表达下列信息：

- 图像原点、像素中心和坐标方向；
- 颜色空间、传递函数、场景/显示参考和预乘方式；
- 数值单位、方向约定、有效范围、无效值和按位复用；
- 精度等级、允许的量化误差和是否参与几何、介质或历史判定；
- 生产者、消费者、有效阶段、alias 关系和外部接口边界。

因此，两个物理格式相同的 `RGBA16F` 图像可能分别表示线性 Rec.2020 radiance、像素 motion、
材质参数或 display-encoded extended-sRGB；同一个图像的 `w` 分量还可能随阶段表示距离、标志、
采样偏移或无效哨兵。编译器无法发现接错资源，维护者必须同时记住 Java、Slang、NRD、FSR、
DLSS RR 和 Streamline 的局部约定。

审查得到七个总判断：

1. **语义和编码是正交维度。** 语义不同的数据必须在 IR、API 和命名中区分；满足相同访问、
   精度和生命周期条件时，它们可以共用一种物理编码或底层 allocation。反过来，同一语义也可
   在 CPU、核心 GPU 和外部 SDK 边界使用不同编码。
2. **核心规范应优先服务 NVIDIA 主路径。** 在不损害数学和精度的前提下，图像坐标、motion、
   颜色和重建输入应尽量直接采用 DLSS RR/Streamline/RTX 主路径可消费的规范形态，避免启用主
   路径后再做全屏翻转或格式换算。NRD 等兼容性回退在自己的 adapter 承担必要转换。
3. **物理复用可以保留，但必须从接口上消除语义复用。** 通过 phase-specific typed view、alias/
   liveness 清单和生成式验证表达复用，不以额外分配图像换类型安全。
4. **精度由信息需求和误差预算决定，不由标量类型决定。** 离散、可比较、不参与连续计算的事实
   优先用整数、枚举、ID 和 bitset 精确表达；连续数据使用满足下游最小精度需求的编码。f32 只是
   当前缺少误差证明时的保守默认，不是强制全链路格式。
5. **CPU 翻译层应拥有静态数据的规范化。** 几何语义恢复、重复面处理、材质通道、线性 Rec.2020
   纹理、mip、OMM 和发光重要性都应尽量一次性前移；但相机 motion、路径状态和动画更新等动态
   数据不能为了“统一”错误地搬到 CPU。
6. **显存首要问题是按渲染像素扩张的数据，而不是 Streamline 的适配副本。** 实时 wavefront
   约为 648 B/渲染像素；NRD 模式 Prime 自有图像约为 291 B/渲染像素。二者合计约
   939 B/渲染像素，尚未计入场景、加速结构及原生 SDK 的内部池。
7. **顺序必须是规范、测试、实现。** 先完成核心 IR、精度/编码规则、NVIDIA 主规范和适配边界，
   再按规范补行为、误差、资源和 benchmark 门禁，最后迁移数据和删除旧转换。当前没有完整
   VMA/`VK_EXT_memory_budget` 归因；在门禁前直接压缩或合并资源无法可靠判断收益和行为漂移。

这里所说的“渲染核心 IR”是现有材质 IR 的扩展，而不是只描述一种材质闭包。它应覆盖来源数据、
场景、纹理、几何、灯光、相机、transport、wavefront、重建、历史、显示和外部 adapter，形成从
CPU 翻译到最终交换链的连续数据谱系。

### 1.1 阶段 0 复审结果（2026-08-31）

阶段 0 已将规范定稿到[渲染核心数据 IR](渲染核心数据IR.md)，并同步修订 GPU 精度、纹理、
材质、Shader 编译边界、函数式架构、透明重建和离线传输文档。此次复审额外确认：

- RR 目前并非原生符合目标坐标；它复用了带 Y 翻转的 `NrdCameraTransform`。Streamline 则在
  `StreamlineInputFlipPass` 再物理翻转 color/depth/motion。目标 top-left 规范因此仍能同时删除
  两类补偿，但迁移必须用同一相机 oracle 验证 jitter、motion 和矩阵。
- 现有纹理文档把 Minecraft sRGB companion view 和逐 hit linear-sRGB→Rec.2020 固化为目标，
  与线性 Rec.2020 工作纹理要求冲突；现已明确为迁移基线，目标由 canonical page 直接采样。
- 现有 GPU 精度文档把所有 world/source normal 与连续字段一律 f32 化，超出了原始精度意图；
  现已改为 exact identity/topology 加用途专属误差合同，同时保留无 ray epsilon 等不可放宽项。
- 文档中的 wavefront 尺寸已经漂移：当前生成 ABI 是实时/离线 path 均 144 B、实时 area 320 B、
  离线 surface/stage 100/112 B。调查账本和相关文档已改为以 `shaders/abi.json` 为唯一来源。

本阶段没有修改生产代码、Shader ABI 或测试预期。VkFormat、record stride、wavefront 重排、
medium 参数编码和 alias 方案有意留到阶段 1 建立 oracle/账本后决定。

## 2. 调查范围与方法

本次覆盖一帧数据从来源到显示的完整路径：

```text
Minecraft / 资源包 / 设置 / 相机
        │
        ├─ CPU 捕获与翻译 ── 几何、材质、纹理页、灯光、OMM、回放
        │
        └─ 帧输入 ───────── 相机、历史、曝光、天文、重建参数
                              │
GPU 场景数据 ── BLAS/TLAS、section、primitive、texture record、light tree
                              │
实时/离线 transport ── path、surface scratch、queue、guide、radiance
                              │
重建输入 ── NRD / FSR / DLSS RR / noisy
                              │
外部适配 ── Streamline、NRD、FSR、NGX
                              │
显示边界 ── SDR sRGB / HDR scRGB / Minecraft UI / 交换链
```

证据来自生产 Java/Slang、`shaders/abi.json`、生成的 ABI、现有架构文档和可执行测试。显存数字按
声明格式和尺寸计算，是不含 allocator 对齐、driver metadata、稀疏驻留、加速结构及原生 SDK
未公开分配的**显式下界**。未能从当前代码精确归因的项目明确标为未知，不用猜测代替测量。

本报告中的通用数据判断服从[渲染核心数据 IR](渲染核心数据IR.md)，精度判断服从
[GPU 几何追踪精度契约](GPU几何追踪精度契约.md)，纹理判断服从
[纹理翻译架构](纹理翻译架构.md)，Shader 拆分服从
[生产 Shader 编译边界契约](生产Shader编译边界契约.md)。

为避免把现行保守实现误写成永久规范，本文区分四个概念：

- **语义**：数据是什么，例如 world-space geometric normal、tangent-space normal texel、medium ID；
- **编码**：数据怎样存，例如 f32x3、RG8_UNORM、oct16、uint16；
- **信息要求**：下游必须保留哪些可区分状态、范围和运算性质；
- **误差预算**：编码误差经过所有消费者后，允许造成的最大数学、事件、几何或图像影响。

精度契约的本意是不得在没有证明的情况下丢失下游需要的信息，而不是规定所有连续量永远使用
f32。例如只表示源 tangent-space 法线纹理且来源本来就是 RG8 时，保留该可审计编码可以完全合理；
world-space normal 必须覆盖斜面等 Minecraft 中少见但合法的输入，其最低精度由最坏合法斜面和
下游 Fresnel、重建、可见性敏感度决定。若一个压缩编码能证明误差可忽略，它同样符合契约。

## 3. 可复用基础和现状约定

统一工作不应把现有正确边界推倒重来，但也不能把现状约定都当成目标规范。下列内容同时标明
可直接复用的设计和需要迁移的兼容实现。

### 3.1 坐标与几何

- `FrameCamera` 是 ray generation 和 reconstruction 共用的相机来源。
- Java/JOML、Slang 和 NRD 内部使用列向量、column-major 矩阵；Streamline 的 row-major 只在
  外部 adapter 生成。
- Vulkan 投影使用 `[0, 1]` reversed-Z；核心重建图像保留正的线性 view Z。
- CPU 世界和相机位置使用 double，GPU 世界位置以 camera-relative f32 表达。
- BLAS 输入是实际提交的 f32 顶点；命中位置、几何法线和动态重心坐标基于同一权威几何。
- 当前几何法线、guide normal、动态重心坐标使用 f32，是缺少更窄编码误差证明时的安全基线；
  将来允许替换为通过最坏输入审计的编码。源/目标身份、介质身份和拓扑应优先保持整数/枚举的
  精确可比较表示，不应过早转换为浮点量再用 epsilon 猜测。

### 3.2 色彩

- 场景工作空间已经统一为 linear Rec.2020 D65。
- 当前 Minecraft albedo atlas 通过 sRGB companion view 解码，再在每次命中时转为 Rec.2020；这
  是现状兼容路径，不是长期的核心纹理 IR。
- NRD、DLSS RR、FSR 输入和 transport radiance 都保持 scene-referred linear Rec.2020。
- NRD 所需 YCoCg、hit distance 和 vendor-specific packing 位于 NRD adapter，而不是核心路径。
- 显示变换才执行 Rec.2020 到 BT.709、tone mapping 和 sRGB/scRGB presentation。

### 3.3 纹理与场景翻译

- `TextureId` 按 `SpriteId` 稳定、单调分配；shader 只看稳定 ID 和 sprite-local UV。
- 不按可见性裁剪合法纹理，`TextureId` 不因 reload 重编号或复用。
- LabPBR normal/optical 在 CPU 侧转换成规范页面，生成 mip 和 gutter；height 只服务几何翻译。
- 几何关系恢复、几乎重合面的语义压缩、介质/双面关系、发光分布和 OMM 都在 BLAS 前构建。

### 3.4 ABI 与诊断数据

- `shaders/abi.json` 已集中记录大量 stride、offset、descriptor、颜色和重建约定，并生成 Java/Slang。
- 几何/材质 ABI 使用显式 record 和 offset，已有 artifact 与 GPU 行为测试。
- 翻译 replay 有 magic、version、ABI ID、解码上限和内容哈希，适合继续作为统一工作的场景门禁。

结论是：Prime 需要把这些局部标准纳入一个可执行的渲染核心 IR。现有“借用 atlas、命中时转
色域”等边界也要由新规范重新判断，不能因为已经实现就自动视为长期标准。

## 4. 数据量化账本

### 4.1 按渲染像素增长的资源

以下均按 render extent 计算；使用 FSR/DLSS 等低渲染分辨率时，应代入实际 render extent，不能
用 display extent 误判。

| 资源组 | 显式字节/渲染像素 | 主要组成 | 备注 |
|---|---:|---|---|
| `BasicRawWavefrontFrame` | 95 B | 2×radiance、normal/roughness、viewZ、metadata、material、position、sun、class、linear output | 含可选 8 B linear output |
| 实时 wavefront | 648 B | 2×144 B path、320 B scratch、40 B queue index | 不含 command/alignment |
| 离线 wavefront | 264 B | 144 B path、112 B scratch、8 B queue index | 另有 16 B/px running mean 等图像 |
| Prime 自有 NRD 图像 | 291 B | 主/反射 noisy、SH、guides、motion、denoised、FSR 输入和 masks | 不含 NRD permanent/transient pool |
| DLSS RR targets | 135 B | signals、两类 normal/motion、position、responsivity、material 等 | 另有 8 B/display px 输出 |
| Streamline 输入转换 | 12 B + color copy | R32 reversed depth、RG32 motion、同格式 HUD-less color | 仅 FG 开启时持有 |

实时 wavefront 的 648 B/px 可进一步拆为：

- 两个 path slot：`144 × 2 = 288 B/px`；
- visible/area guide 区：`32 B/px`；
- 两个 surface slot：`112 × 2 = 224 B/px`；
- 两个 staged light slot：`12 × 2 = 24 B/px`；
- detached guide：`40 B/px`；
- 10 个 queue index：`10 × 4 = 40 B/px`。

NRD 路径与实时 wavefront 的显式合计为 **939 B/渲染像素**：

| render extent | 实时 wavefront | Prime 自有 NRD 图像 | 合计下界 |
|---|---:|---:|---:|
| 960×540 | 320.36 MiB | 143.87 MiB | 464.23 MiB |
| 1280×720 | 569.53 MiB | 255.76 MiB | 825.29 MiB |
| 1920×1080 | 1,281.45 MiB | 575.46 MiB | 1.81 GiB |
| 2560×1440 | 2,278.13 MiB | 1,023.05 MiB | 3.22 GiB |

这解释了为什么“每像素少几个字节”会显著影响显存门槛，但也说明任何压缩都必须优先针对真正
长寿命、全分辨率、重复存储的数据，而不能拿几何/介质正确性换空间。

### 4.2 固定 GPU 数据

| 资源 | 估算 | 观察 |
|---|---:|---|
| 8192×4096 RGBA16F starmap | 256 MiB | Shader 只采样 `.rgb`，alpha 未被消费；无 mip |
| atmosphere 全部 LUT/clipmap | 约 60.94 MiB | aerial radiance 32 MiB；shadow depth/hierarchy 各 10 MiB |
| realtime STBN | 12 MiB | 预计算、只读，设计合理 |
| BSDF LUT | 约 1.71 MiB | 固定参考数据，压缩收益低且风险高 |
| 合计 | 约 330.65 MiB | 不含上传暂存 |

starmap 的四条启动 upload stripe 合计另占 256 MiB host-visible 暂存，STBN 与 BSDF LUT 各自也有
约 12 MiB 和 1.71 MiB 暂存，直到提交完成后释放。固定资源不随分辨率增长，但会直接抬高最低
显存和启动峰值。

starmap 是明确的 P1 候选：先确认源数据动态范围、alpha 恒定性、目标 GPU 格式支持，再比较
RGB packed、BC6H 或离线多级表示的辐射误差、天空图像误差、采样成本和启动峰值。不能仅因 alpha
未用就假定某个 3 通道 Vulkan 格式一定具有更低物理占用或更好的采样性能。

### 4.3 场景相关数据

- 静态三角形顶点下界为 `9 × f32 = 36 B/triangle`；`PrimitiveRecord` 为 32 B，但矩形的两个
  triangle 可以共享 primitive 语义。
- `SectionRecord` 为 96 B，另有 surface relation、light tree/leaf/emitter、BLAS/TLAS、instance、
  OMM 和 allocator 开销。
- normal/optical 页面按实际矩形分页；albedo 当前借用原版 atlas，因此本账本尚不含未来 linear
  Rec.2020 canonical color pages。迁移后仍应使用实际矩形分页，避免每纹理一个 image、最大尺寸
  镜像或按可见性加载。
- texture record 为 32 B/`TextureId`。ID 单调且不复用，长时间多次 reload 后可能出现稀疏空洞；
  24-bit ID 空间对应的理论完整表为 512 MiB。当前没有证据表明这是常见瓶颈，应先记录 catalog
  高水位和实际有效比例。

### 4.4 尚未计量的数据

当前代码没有完整的 GPU 内存归因，因此以下成本不能从静态清单得出：

- VMA allocation、block 对齐、碎片和 residency；
- BLAS/TLAS、scratch、compaction 前后大小；
- NRD permanent/transient pool 的逐帧和峰值合计；
- FSR、NGX/DLSS、Streamline driver/native 内部分配；
- Minecraft/Prime 共享 atlas 和交换链归属；
- resource reload、resize、backend 切换时新旧 generation 短暂并存的峰值。

这不是文档问题，而是后续统一的 P0 测量缺口。应在 VMA 分类标签、NRD description 和 Vulkan
memory budget 的基础上输出可机器比较的逐类账本，并在外部 SDK create/destroy 前后采样预算。

## 5. 坐标、矩阵、深度和运动

### 5.1 当前规范岛

Prime 内部实际存在一个可用的核心约定：

- render image 的 row 0 对应投影中的 NDC `y = -1`；
- 像素样本以中心 `+0.5` 为基准，jitter 是额外 sample displacement；
- 世界位置为 camera-relative f32，CPU 相机绝对位置为 double；
- 核心 depth 是正的 linear view Z；
- 核心 motion 是 current-to-previous，但不同消费者使用 pixel、UV 或 2.5D 单位；
- 核心矩阵使用 column-major/列向量。

已有 `FrameCameraTest`、`NrdCameraTransformTest`、FSR/DLSS motion contract 和
`StreamlineFrameConstantsTest` 覆盖了若干关键符号和重投影行为。

### 5.2 外部边界差异

| 消费者 | motion | depth | 图像/矩阵适配 |
|---|---|---|---|
| NRD | screen-pixel current→previous 2.5D | linear view Z | projection Y adapter |
| FSR | normalized UV current→previous | reversed-infinite depth | 独立 FSR depth/motion |
| DLSS RR | normalized UV current→previous，另有 spec motion | linear view Z | RR target contract |
| Streamline FG | pixel scale、current→previous | reversed-infinite depth | top-left 资源、row-major constants、垂直翻转 |

`StreamlineInputFlipPass` 当前执行一次全屏 compute，把 Prime view Z 转成 reversed-infinite depth、
垂直翻转像素并反转 motion Y；另执行一次 color blit。它增加一组 R32、RG32 和 HUD-less color
持久图像。它正确隔离了现有两套约定，但对 NVIDIA 主路径而言仍是应被消除的迁移成本：核心若
直接使用同一图像坐标，RR/Streamline 就不应为了 Y 方向再执行专门的全屏转换。

### 5.3 风险

- “jitter” 同时被用于 sample offset、projection displacement 和外部 SDK offset；它们的符号并不
  相同。Streamline 当前提交 `(-x, +y)`，FSR 和内部投影又有各自 inverse/flip。
- `float2 motion` 不能说明 pixel/UV、current→previous/previous→current、是否含 camera motion、
  是否含 jitter、Y 方向和无效值。
- reversed depth、linear view Z 和命中距离均可由 `R32F` 表示，接错后格式验证仍会通过。
- 每个 adapter 独立重新推导矩阵和符号，缺少一个跨后端、共享场景的 oracle。

### 5.4 统一目标

核心图像坐标应改为 NVIDIA 主路径直接可用的 top-left 规范：row 0 是图像顶部，motion 使用
current-to-previous，基础二维 motion 优先使用 RR/Streamline 可直接消费的 normalized UV 语义。
NRD 的 screen-pixel 2.5D motion 和投影 Y 变换由 NRD adapter 生成。最终定稿时仍须用实际 RR、
Streamline tag 和 raygen corner oracle 逐项确认像素中心、jitter 符号及无效值，不能只凭“top-left”
三个字推断全部约定。

NVIDIA-first 不等于把每个 native wire format 传播到所有 shader：

- 全屏图像翻转、逐像素 motion 单位换算和重复颜色转换是应优先消除的高成本摩擦；
- row-major native matrix 可以从规范相机在 CPU 边界序列化，成本很小，不必强迫 Shader 数学改用
  不自然的矩阵布局；
- linear view Z、reversed depth 和 hit distance 是三个不同语义。主路径需要的派生值应由最近的
  生产阶段直接写出或融合生成，而不是事后另起全屏 pass；不能用一个含义模糊的 R32 代替三者；
- NRD/noisy 等兼容路径明确承担与核心 NVIDIA 规范之间的转换成本。

在 CPU/构建层引入零额外 GPU 存储的语义值或 descriptor，例如：

- `SampleOffsetPixels`
- `ProjectionJitterPixels`
- `MotionPixelsCurrentToPrevious`
- `MotionUvCurrentToPrevious`
- `LinearViewZMetres`
- `ReversedInfiniteDepth`
- `NvTopLeftImageCoordinate`
- `NrdImageCoordinate`

由一个 `CameraContract` 从 NVIDIA-aligned 规范相机/图像空间生成 RR/Streamline 直接输入，以及
NRD/FSR/noisy 的 adapter 常量。类型必须阻止单位和方向混用，但 shader 中仍可落为普通
`float2/float4`，不能为类型化引入运行时对象或扩大 push constant。

## 6. 色彩与显示数据

### 6.1 当前颜色链

```text
sRGB 资源/atlas
  └─ hardware/manual EOTF → linear sRGB
       └─ matrix → scene-referred linear Rec.2020
            ├─ transport / NRD / RR / FSR
            └─ Rec.2020 → linear BT.709 → Reinhard-Gamut → encoded sRGB
                 ├─ RGBA8 SDR/UI baseline
                 └─ RGBA16F encoded extended-sRGB HDR
                      └─ EOTF → linear scRGB swapchain
```

核心 linear Rec.2020 不只是性能选择，而是正确性边界。encoded sRGB 数值不能被当作线性量参与
插值、mip、混合或 transport；源纹理应在 CPU 捕获/翻译时完成 EOTF 和 gamut conversion，并在
linear Rec.2020 中生成 canonical mip。GPU 生产采样得到的应当已经是 linear Rec.2020，不再在每次
hit 执行 sRGB→Rec.2020。

这不意味着 canonical albedo 必须使用 RGBA16F。颜色**语义**固定为 linear Rec.2020，物理编码可
根据合法输入范围、alpha、过滤、设备支持和端到端误差预算选择 linear UNORM、float 或块压缩。
初始迁移可用保守高精度格式建立 oracle，再在不改变语义的前提下审计更窄编码。额外 renderer-
owned texture storage 是这项正确性边界的成本，应通过分页、紧凑编码、动画增量上传和删除命中
热路径转换回收，而不是继续让 encoded source atlas 成为生产 IR。

### 6.2 具体问题

1. CPU 侧存在多份 sRGB decode/Rec.2020 系数实现，例如 emission importance 和 voxel/material
   翻译。它们今天数值接近，但没有由同一数据源生成，未来容易漂移。
2. 当前 albedo 的 mip/filter lineage 由 Minecraft atlas 和 sRGB view 决定，Prime 不拥有从源 texel
   到 linear Rec.2020 canonical mip 的完整数据谱系；每次 hit 还重复执行 gamut conversion。
3. `RGBA16F` 既表示 scene-linear Rec.2020，又表示 display-encoded extended-sRGB；`VulkanImage`
   无法区分两者。
4. HDR 世界先写 encoded extended-sRGB，再在 `hdr_present` 全屏 pass 中执行 EOTF 回到 linear
   scRGB。tone mapper 的 hue 操作可能仍需编码域，但世界结果可以在第一阶段完成最终线性化，
   避免在第二阶段再次逐像素 EOTF；需要与 UI coverage 恢复逻辑分开评估。
5. HDR UI 通过 encoded RGBA8 最终色和 alpha 反推 premultiplied UI，再在线性域合成。现有文档
   已明确非 source-over 混合无法精确恢复。这是接受过的边界近似，但数据类型应明确命名为
   `EncodedSrgbPremultiplied`，不能被误当作 scene color。
6. SDR 手动编码值写入 `RGBA8_UNORM` 而非 sRGB storage；格式名看不出“已经 encoded”。

### 6.3 统一目标

- 用一个生成源维护 CPU/Slang 色彩矩阵、EOTF/OETF 常量和白点标识，并做 CPU/GPU 差分测试。
- encoded source texture 在 CPU 翻译边界转为 linear Rec.2020 canonical texture；mip、gutter、动画
  帧和发光统计都从同一线性数据生成。alpha/coverage 作为非颜色语义独立处理。
- starmap 等离线固定颜色资产也在构建时转为 linear Rec.2020，删除每次环境采样的色域矩阵；
  atmosphere 的光谱 LUT 仍按自身 spectral semantic 保存，不能误作 RGB texture 统一。
- 每个 image contract 明确 `scene/display`、primaries、white point、transfer、alpha 和范围。
- 将 `LinearRec2020Radiance`、`EncodedSrgbDisplay`、`LinearScRgbDisplay` 作为不同语义，即使物理
  格式都为 RGBA16F。
- 把 vendor 需要的色彩 packing 留在 adapter；核心不保存 NRD/NGX 的编码格式。
- 单独 benchmark HDR 世界输出线性化与现有 encode→store→load→decode，保留完全相同的 tone
  curve、色相和绝对亮度契约。

## 7. 纹理、采样和材质页面

### 7.1 物理布局

现有 normal page 使用 RGBA8_UNORM 表示 tangent normal XY、AO 和 distribution roughness；optical
page 的 R/A 是可滤波连续量，G/B 是 mip0 `Load` 的分类量。相同物理格式承载两套完全不同的
通道含义，默认 ARGB 值也依赖魔数。

`PrimitiveRecord` 以 UQ0.16 保存四角 UV，tint 使用源 RGBA8，`TextureId`/emitter/dynamic payload
共享 24-bit 字段，UV density 为 f32，tangent 使用 oct/snorm2x16 和 handedness。tangent 是 shading
basis，不是几何法线，因此不直接违反几何精度契约；但需要有用途专属名称和角误差门禁。

### 7.2 热路径观察

材质访问路径会：

- 从 32 B texture record 中按需解码 page、rect 和 flags；
- 对 bindless page/atlas 查询 dimensions；
- 把 source rect 转为 normalized UV；
- 对 optical 分类通道把归一化 float 再恢复为语义 byte；
- 对 albedo 执行 tint sRGB decode 和 linear sRGB→Rec.2020 转换。

这些操作是否是瓶颈不能靠源码观感决定。候选方案包括把 rect 预解码为 scale/bias、为分类通道
使用整数 load/view、按访问频率拆分 record 或在 subgroup/path 内复用解析结果；每一种都会改变
record 尺寸、加载次数、cache 行为或 descriptor 数量，必须以 Shader 编译统计和 GPU benchmark
选择。

### 7.3 应前移与不应前移的工作

应继续留在 CPU/resource-generation：

- source albedo/tint 的 sRGB EOTF、linear Rec.2020 转换和 canonical mip；
- LabPBR 文件解析、通道规范化、normal 修正、mip/gutter 和 page packing；
- height 到几何的位移；
- 动画 catalog 和实际变化矩形；
- OMM opacity 分类；
- emitter radiance 与重要性分布；
- 纹理 record 中与相机/路径无关的派生字段。

不应盲目前移：

- 依赖当前 mip、ray cone、动画帧或路径命中的采样；
- 为消除一次算术而增加一次随机全局内存读取的 indirection。

这会改变当前实现中“albedo 借用 Minecraft atlas”的边界；阶段 0 已同步修订
[纹理翻译架构](纹理翻译架构.md)，把它降为迁移基线。需要保留的是稳定 `TextureId`、完整 catalog、矩形分页和
不按可见性裁剪，不是 encoded source atlas 本身。动画不必每帧重建全 catalog；CPU 对变化 rect
执行相同的 decode/gamut conversion 后增量上传 canonical texel。

### 7.4 维护改进

- 为 normal/optical 定义生成式 channel schema 和 typed CPU records，消除 ARGB 位序魔数。
- optical/material 的分类通道使用整数/枚举 semantic，并优先选择整数 load/view；不要先归一化为
  float，再乘回 byte 做相等比较。若因物理页复用仍存于 UNORM，窄 accessor 必须执行位级可逆
  解码并由 artifact/GPU test 证明所有 256 个码点。
- 将泛化的 `primePackOctahedralUnitVector` 拆成用途名，例如 packed tangent 和 packed area moment；
  函数名本身应阻止误用于 geometry/guide normal。
- 给 UQ0.16 UV 建立独立精度范围，特别覆盖大于 4096、接近 32768 的纹理边界和非整齐 rect。
- 记录 `TextureId` 高水位、当前有效数和 record table 空洞率，再决定是否值得增加 stable-ID 到
  dense-record 的热路径 indirection。

## 8. 几何、实例和场景记录

### 8.1 当前数据边界

翻译层已经把 Minecraft quad/peer/surface/block/fluid facts 转为：

- camera/cluster/section-relative f32 triangle positions；
- 32 B primitive material/UV/tangent record；
- surface relation 和精确介质拓扑；
- static/dynamic section、实例 tint、previous positions；
- light tree、emitter、world light path 和 OMM。

这是“一次性转换前移”的主要成功案例。尤其是几乎重合面、双面、overlay、边界、玻璃和水的
语义必须在 CPU 翻译层恢复，不能在 any-hit 里用 epsilon 猜测。

### 8.2 风险与零碎问题

- `CpuSectionMesh` 拥有不可变生命周期，但 Java 数组 getter 实际仍是 borrowed mutable storage；
  所有权只靠约定。
- `SectionRecord.lightAddress` 在静态 cluster 表示 light tree，在 dynamic cluster 表示 previous
  position buffer。相同 address 字段的意义由 section 类型隐式决定，容易产生错误 storage load。
- primitive 的 24-bit payload 在 texture、emitter 和 dynamic 语义间复用，只有 flags 决定解释。
- position buffer 和 previous-position buffer 当前都是完整 f32，是尚未完成误差审计时的保守
  基线。任何更窄表示都必须覆盖合法动态几何，并证明不会改变 BLAS、重心、motion、自交和身份；
  不能只凭常见方块坐标范围假设 FP16 足够。
- record layout 由 ABI 生成，但字段的单位、tagged union 和所有权没有生成。

建议用显式 tagged union/schema 表达 `SectionRecord` 与 primitive payload。若拆成不同物理 record
会增加静态热路径 stride，应优先保留 96/32 B 布局，只生成安全 accessor 和验证；只有 benchmark
证明值得时才改 ABI。

## 9. Wavefront、队列和中间编码

### 9.1 记录现状

实时 path record 为 144 B，其中 transport 基础 112 B 保存：

- origin、ray direction、throughput、previous BSDF PDF；
- source primitive/section identity、path/denoiser control；
- 两层介质 extinction 和 IOR；
- previous light normal。

附加 32 B 保存 PSR/guide normal 与 roughness。surface scratch 和 trace payload 都是 112 B；
detached guide 是精确 40 B ray record。离线 path 同为 144 B，但最后 32 B 用于 beauty metadata。

这些记录当前以 f32 保留连续几何/transport 值、以整数保留部分身份，是安全的保守基线。离散
身份应进一步全部转为整数/枚举；连续字段只有在误差审计后才可换窄编码。主要问题不是能从字段
名直接断定谁“太宽”，而是 path 分支与阶段的 liveness 没有机器化表达，导致两个完整 slot 和
大块 scratch 按所有像素常驻。

### 9.2 高风险精度发现

#### A. shadow medium 以 FP16 归一并用 epsilon 比较

`primeShadowCanonicalExtinction` 把 f32 extinction 显式 round-trip 到 FP16，
`primeShadowSameMedium` 再以相对 `1/1024` 判断两个介质相同。现有 GPU property test 证明的是
这套近似行为本身稳定，而不是它符合当前精度契约。

这里的问题不是“extinction 永远必须 f32”，而是把一个连续、可量化的光学参数同时当作离散介质
身份，并靠有损 round-trip 与 epsilon 恢复拓扑。身份和参数必须拆开：

- CPU 翻译层为相邻介质建立明确、稳定的 medium identity；
- shadow payload/状态携带精确 identity，以及达到透射误差预算的 extinction 编码；
- 相同介质用 identity/拓扑判定，不用 extinction 浮点近似反推；
- 迁移前用透明嵌套、相近 extinction、跨 section 和长 shadow path 行为测试锁定结果。

identity/parameter 解耦是 P0 规范问题。extinction 最终使用 f32、FP16、log 编码还是材质表索引，应
由最大合法距离上的 transmittance 误差审计决定；若用 medium ID 间接访问规范材质表，还可同时
减少 payload 并保持精确比较。

#### B. 实时 `etaScale` 使用 FP16

实时 wavefront 把 `etaScale` 压为 FP16，注释说明它只改变 Russian roulette survival，幸存路径
重权后估计期望仍无偏。现有测试容许约 `6e-4` 的数值误差。

但 survival 概率改变会改变离散路径事件和随机数映射；“期望无偏”不等于与参考行为和分布完全
一致。应补充路径分布、能量和图像误差证据，再决定：

- 保留 FP16、改用其他紧凑编码，并把允许误差写入明确的 transport 精度合同；或
- 如果没有更窄编码能通过审计，才恢复完整 f32，并从其他不敏感 control 位或 liveness 优化中
  找回空间。

#### C. 其他有损字段

- tangent-space source normal 可以保留来源 RG8 或同等可审计编码；一旦提升为任意斜面的
  world-space shading/guide normal，其编码必须覆盖完整合法方向并通过下游角度、Fresnel 和重建
  误差门禁。
- area/SH reconstruction direction 以 FP16 或 octa 表示。它们不是 geometry normal，但会影响
  NRD reconstruction；是否保留取决于角误差和图像误差门禁，不取决于“是否 f32”。
- ray cone width/mip bias 以 half2 进入 push constant，只影响 LOD。应由 typed `RayConeParameters`
  在 ABI 边界打包并有纹理误差测试。
- camera sample 打包进 position `w`；若读取阶段或 backend 改变，很容易被误解为几何分量。

### 9.3 phase alias 和通道过载

下列复用节省了显存，但目前主要靠注释和调用顺序维持：

- `transportMetadata` 先是 raygen scratch，随后被 reconstruction preparation 覆写为 motion；
- reflection targets 在某些 backend 默认 alias primary targets；
- `material.a` 可表示 surface distance、sky 负哨兵或其他 validity；
- `primaryPosition.w` 在 NRD 可放 packed camera sample，在 RR 又携带 signed distance/motion validity；
- `displayPosition.w` 以 bitcast 存 material flags；
- `stableRadiance.a` 在透明 guide 阶段临时保存可见 primary distance。

建议保留底层 image alias，但不再把一个 `RawWavefrontFrame` 全字段接口暴露给所有阶段。由数据
合同生成 phase view，例如 `RaygenScratchView`、`VisibleSurfaceGuides`、`NrdPrepareInputs` 和
`RrPrepareInputs`；构建时验证同一 alias group 的 lifetime 不重叠。

### 9.4 性能方向

wavefront 是最大按像素成本，P1 benchmark 应逐阶段记录：

- 每个 slot/field 的首次写和最后读；
- active path 比例、分叉比例、透明/delta guide 比例；
- queue occupancy 和两 slot 同时活跃的像素比例；
- surface/staged-light/detached-guide 的实际重叠生命周期；
- record load/store 字节、cache miss、寄存器和 spill。

然后再选择 conditional allocation、阶段 alias、AoS/SoA 拆分、queue compaction 或字段移除。静态
看起来“空闲”的 lane 可能是为了窄 megakernel、对齐或减少随机读取，不能只按结构体大小裁剪。

## 10. 重建后端和外部 SDK

### 10.1 共同问题

NRD、FSR、DLSS RR 和 Streamline 都有合法但不同的数据契约。当前代码已经把转换放在各自 pass，
避免了隐式混用；但 canonical source 没有类型化，而且当前 canonical 形态没有优先对齐 NVIDIA
主路径，导致 RR/Streamline 仍承担可消除的转换。后端 target set 也大多按固定大集合分配。

`NrdImages` 中 Prime 自有的 291 B/px 包含主路径、reflection、SH、denoised、display position、
FSR motion/depth/masks 等资源。部分资源是模式或功能专用，却由一个长寿命对象同时持有。DLSS RR
也有独立的 135 B/px target set。

### 10.2 统一目标

- 定义一组语义完整、物理形态优先与 NVIDIA 主路径对齐的 canonical outputs。对齐只选择在核心
  数学上同样正确、又能删除高成本转换的坐标、单位和编码；不把 opaque native struct 当作核心 IR。
- RR/Streamline 声明可直接消费的 canonical semantic；NRD/FSR/noisy 声明所需 adapter。资源规划器
  只分配被选 backend/feature 实际需要的 targets。
- 通过 alias/liveness 规划复用不同时段的相同格式图像，而不是让 Java getter 静默 alias。
- 把 NRD description 中的 permanent/transient pool 格式与 downsample factor 纳入内存账本。
- Streamline 保持高风险功能隔离；核心迁移后 top-left 和基础 motion 不应再转换，opaque tag、
  reversed depth 派生、HUD-less color/UI mask 和 native 生命周期仍属于 interop adapter。

### 10.3 不能承诺的一次性统一

下面这些差异是外部接口本身要求的，无法靠改一个内部格式全部消失；但成本应由兼容路径承担，
不能平均分摊给 NVIDIA 主路径：

- linear view Z 与 reversed depth；
- pixel motion、UV motion 和 2.5D motion；
- NRD normal/roughness、DLSS RR normal/albedo/specular motion 的不同格式；
- row-major native constants 与 column-major shader math；
- display extent 输出与 render extent signals。

正确的“一劳永逸”是 NVIDIA 主路径尽可能直接消费核心 IR，兼容路径的差异只存在于有声明、有
测试、有计量的边界，而不是让所有 SDK 直接共享一张含义模糊的图像。

## 11. 固定表、灯光、天空和零碎数据

### 11.1 Atmosphere 和 sun shadow

- atmosphere 的 low/high spectral pair 是八波段拆分，不是无意义重复；不得在没有光谱等价证明时
  合并为 RGB。
- aerial radiance 32 MiB 是 atmosphere 最大单项，aerial transmittance 8 MiB；格式压缩属于 P2，
  需要天空/雾路径图像误差和 banding 测试。
- sun shadow 使用两 bank、五 cascade 的 R32 depth 和五张 RG32 hierarchy，固定约 20 MiB。
  `±1e20` 等 sentinel 和 sun-basis coordinate 应进入 typed contract。

### 11.2 Light data

- CPU 已前移构建 emitter、cell alias、tree/leaf 和 power distribution，这是正确边界。
- `LightEmitter` 96 B、`LightNode` 32 B 等布局应加入统一账本。
- 非几何的 packed cone/direction 可以保留，但必须按用途命名并有角度/能量误差边界，不能提供
  一个容易被 geometry normal 误用的泛化压缩入口。

### 11.3 STBN、BSDF LUT、曝光和历史

- STBN 和 BSDF LUT 是小而稳定的只读表，不应成为首轮压缩目标。
- auto-exposure histogram/state 体积很小，但其 logarithmic luminance、EV 单位和历史 reset 条件
  仍应写入数据合同。
- history validity、camera discontinuity、resize/backend switch reset 已有状态测试；后续合同应把
  generation 和 reset owner 也纳入资源生命周期。

### 11.4 CPU 设置和帧输入

`IntegratorFrameInput` 是较好的设备地址无关 value object；quarter-EV、roughness step 等配置也有
明确离散单位。`packedRayCone` 是例外：打包细节穿过了多层 Java API。应让上层传语义值，只在
push constant writer 处打包。

| D-02 | P0 | shadow 由量化 extinction + epsilon 反推 medium identity | 连续参数与离散身份混用，拓扑不可精确比较 |

| D-04 | P0 | 无完整 VMA/native GPU 内存归因 | 无法可靠优化显存门槛和峰值 |
| D-05 | P0/P1 | source sRGB atlas 仍是生产颜色源 | canonical mip/filter 谱系不完整，hit 重复转色域 |
| D-06 | P1 | 核心图像坐标未对齐 RR/Streamline | NVIDIA 主路径增加全屏翻转、motion/depth 适配 |
| D-07 | P0/P1 | realtime `etaScale` FP16 改变 roulette 分布 | 需证明误差可忽略或选择满足要求的编码 |
| D-08 | P1 | wavefront 648 B/px | 最大显式按像素存储和带宽入口 |
| D-09 | P1 | NRD 自有 targets 291 B/px + 未计 native pool | 高分辨率显存门槛 |
| D-10 | P1 | 8K RGBA16F starmap 256 MiB，alpha 未用 | 固定显存和启动暂存峰值 |
| D-11 | P1 | HDR world encoded store 后再次 EOTF | 全屏读写/数学和语义混淆 |
| D-12 | P1 | 材质 record/page 在 hit 热路径重复适配 | 可能增加带宽、ALU 和 cache 压力 |
| D-13 | P1 | backend targets 固定大集合 | 未启用特性仍可能常驻资源 |
| D-14 | P2 | `TextureId` 单调表可能累积空洞 | 长 reload 会话的潜在显存增长 |
| D-15 | P2 | CPU/Slang 色彩常量与通道 schema 多份实现 | 长期漂移风险 |
| D-16 | P2 | atmosphere、light、shadow 的语义未类型化 | 局部维护和误用风险 |
| D-17 | P2 | CPU borrowed arrays 所有权不由类型保证 | 并发/生命周期错误风险 |

P0 表示建立统一工作前必须解决或建立门禁；P1 是有明显性能/显存收益的主体；P2 是测量后逐步
收敛的维护项。等级不是要求在一个提交中同时改完。

## 13. 渲染核心数据 IR 规范

### 13.1 IR 范围

该 IR 是[统一材质 IR 与闭包](统一材质IR与闭包.md)的上位扩展，覆盖整个 renderer core，而不是
取代材质 IR 的专用拓扑。建议分为相互连接的层：

| IR 层 | 主要数据 | 规范职责 |
|---|---|---|
| Source IR | Minecraft sprite、LabPBR、block/fluid facts、绝对坐标 | 只存在于捕获边界，保留来源身份和编码 |
| Scene IR | geometry、primitive、material、texture、medium、light、OMM | CPU 翻译后的稳定 GPU 场景语义 |
| Frame IR | camera、extent、jitter、history、exposure、astronomy | 每帧规范坐标、单位和 generation |
| Transport IR | ray、path、surface、medium stack、queue、radiance | 实时/离线路径状态与精度要求 |
| Reconstruction IR | guides、motion、depth、albedo、normal、signals | NVIDIA-aligned canonical inputs 与 fallback adapter |
| Presentation IR | scene/display color、tone state、UI coverage、swapchain | 唯一显示转换边界 |
| Interop IR | RR、Streamline、NRD、FSR、native handles | 显式外部 wire format 和所有权 |

每层必须声明上游来源和下游消费者。跨层转换只能由指定 owner 执行一次；不能让下游重新解析
Source IR，也不能让 native interop 类型反向进入 Scene/Transport IR。

### 13.2 语义与编码分离的机器来源

在现有 `shaders/abi.json` 上扩展，或新增一个由同一 generator 消费的 `renderer_ir.json`。语义
合同和物理编码分别声明，再由 binding 把二者组合：

```json
{
  "semantic": {
    "id": "motion.visible.current_to_previous",
    "channels": ["dx", "dy"],
    "coordinateOrigin": "nv-top-left",
    "unit": "normalized-uv",
    "direction": "current-to-previous",
    "validity": "explicit-mask",
    "precisionRequirement": "reprojection-under-quarter-pixel"
  },
  "encoding": {
    "id": "motion-rg16f",
    "storage": "R16G16_SFLOAT",
    "roundTrip": "audited-lossy",
    "range": "finite"
  },
  "binding": {
    "producer": "rr-prepare",
    "consumers": ["dlss-rr", "streamline"],
    "lifetime": ["rr-prepare", "present"],
    "aliasGroup": null
  }
}
```

颜色语义再声明 primaries、white point、transfer、scene/display reference 和 alpha；buffer 编码再
声明 stride、record、address space、ownership 和 count source；tagged lane 声明判别字段、bitcast
和 sentinel。一个 encoding 可以被多个 semantic 复用，但 Java/Slang API 暴露的是 semantic view，
不能暴露无类型的“某张 RGBA16F”。

### 13.3 约束优先级

能靠结构约束的，不靠团队记忆：

1. **类型与 IR schema**：非法组合无法构造，例如 normalized motion 不能传给 pixel-motion API；
2. **生成式 API/accessor**：字段只能通过所属 semantic 读取，tagged union 先检查 discriminator；
3. **构建期验证**：format、usage、extent、stride、descriptor、lifetime 和 alias 图不一致即失败；
4. **边界运行时验证**：外部/native/config 输入在进入可信域时检查，生产 shader 热路径不重复检查；
5. **API 与命名**：Slang 受类型系统限制时，用完整语义名和窄 accessor 表达约束；
6. **文档约定**：只记录无法由前五项表达的原因、误差证明和外部来源。

不得把关键 channel 语义只写在注释或调查报告里。若两个语义共用 allocation，调用者看到的仍应
是不同 phase view；底层 alias 只由 resource planner 持有。

同一 IR 应生成或验证：

- Java semantic handle/descriptor、创建参数和生命周期 API；
- Slang resource declaration、channel accessor、enum/bitfield 和常量；
- Vulkan debug label；
- 每像素/固定/场景相关的静态字节账本；
- descriptor、extent、usage、format、alias/lifetime artifact tests；
- 文档表格，避免报告和代码再次漂移。

Java wrapper 不应为每个像素或 dispatch 创建对象；它只存在于资源规划和 command recording 边界。
Shader accessor 应被编译为现有的普通 load/store，不扩大生产 entry 的依赖闭包。

### 13.4 信息与精度等级

精度等级描述“至少要保留什么”，编码只是满足该要求的一种方案：

| 等级 | 典型数据 | 最低信息要求 |
|---|---|---|
| I-exact-discrete | source/medium/primitive ID、enum、flags、validity、queue state | 整数/枚举位级可逆，不转换为近似 float 比较 |
| I-source-lossless | RG8 tangent normal、RGBA8 tint、源 UV grid | 至少保留来源可表达的全部状态；可原编码或无损重编码 |
| I-geometric | 顶点、重心、world geometric/guide normal | 覆盖全部合法斜面和身份，误差不得改变命中、自交、Fresnel 或重建 |
| I-transport | IOR、extinction、PDF、eta、throughput | 误差经最长合法路径后仍满足事件、分布、能量和图像界限 |
| I-radiance | radiance、history、LUT | 声明范围、clamp 和累积误差；允许通过证明的 float/UNORM/块压缩 |
| I-presentation | motion、depth、display color | 满足重投影、重建和绝对显示误差，并符合 NVIDIA 主输入契约 |

例如 RG8 tangent normal 可以满足 I-source-lossless；同一 texel 被转换成 world-space normal 后，必须
重新按 I-geometric 审计，不能因来源是 RG8 就继续假设 RG8 足够。f32、FP16、oct、UNORM、ID
查表都只是候选编码；选择依据是信息保留和端到端误差，而不是格式名称。

## 14. 一次性转换的前移决策

| 数据/转换 | 建议边界 | 原因 |
|---|---|---|
| quad/overlay/介质/双面/重复面语义 | CPU 翻译层 | 与场景静态事实相关，移出 any-hit/transport |
| medium identity 与拓扑 | CPU 翻译层生成，GPU 精确携带 | 消除 extinction epsilon 反推 |
| LabPBR 通道、mip、gutter、page | CPU 资源生成 | 已实现；避免 shader 重复解析源格式 |
| encoded sRGB albedo/tint → linear Rec.2020 | CPU 纹理翻译 | 正确性边界；canonical mip/filter 同在线性工作空间 |
| OMM、emitter importance、light tree | CPU 构建 | 已实现；长期复用 |
| 色彩矩阵与通道常量 | 单一生成源 | 消除 CPU/Shader 多份手写实现 |
| texture rect scale/bias | 候选 CPU 派生字段 | 需比较 record 增长与 hit ALU/cache 收益 |
| starmap → linear Rec.2020 与紧凑编码 | 离线构建 | 固定资产；删除每次采样转色域并审计存储误差 |
| 相机绝对到 camera-relative | CPU 每帧边界 | 保留 double 精度后一次下放 |
| RR/Streamline 坐标和基础 motion | NVIDIA-aligned 核心生产者 | 主路径直接写规范值，删除专门 flip/convert pass |
| NRD/FSR/noisy depth/motion | fallback GPU adapter | 每帧动态差异由兼容路径承担并融合到最近 pass |
| path scatter、throughput、ray cone LOD | GPU transport | 路径依赖，无法静态前移 |
| animated texture changed rect | CPU 确定范围，GPU 上传/生成 | 只处理实际变化区域 |
| HDR tone/display transfer | GPU display 边界 | 与曝光、屏幕峰值和 UI 合成动态相关 |

原则是先把**与帧和路径无关、可复用的正确性转换**前移，再为 canonical 数据选择满足误差预算的
最窄编码。linear Rec.2020 texture 即使初期增加 renderer-owned storage 也不能省略；随后应通过
分页、紧凑编码和删除旧 atlas 依赖降低净成本。纯性能派生仍需同时核算副本、上传、record stride、
cache 和 shader ALU，不能把“CPU 前移”本身当作优化证明。

## 15. 测试与 benchmark 门禁

### 15.1 现有覆盖

目前已有较好的局部覆盖：

- `FrameCameraTest`、`NrdCameraTransformTest` 和各后端 motion/constants test；
- `ShaderAbiTest`、primitive packing、texture page/layout/property tests；
- GPU transport、NRD、颜色采样和数值 property tests；
- translation replay、语义 oracle、取消和几何精度回归；
- native NRD/FSR/DLSS/Streamline contract 与执行测试。

这些测试能保护局部行为，但还不能证明所有 backend 对同一 canonical input 的解释一致，也不能
防止语义相同/格式相同的资源被接错。

### 15.2 规范定稿后的第一批门禁

以下测试必须从已经定稿的 IR 条款生成输入和预期，不能让现状测试反过来定义规范。规范中的每个
MUST、合法编码和误差预算都应能路由到一个行为、artifact、数值或资源计划门禁。

1. **Data contract artifact test**：每个资源的 format、extent source、usage、descriptor、channel、
   alias 和 lifetime 与生成合同一致。
2. **跨 adapter 相机 oracle**：以画面四角、中心、天空、静态点、移动物体和 camera cut 为输入，
   同时验证 NRD、FSR、RR、Streamline 的 depth/motion/jitter 重投影。
3. **端到端颜色 oracle**：CPU/Slang sRGB↔Rec.2020、tone mapping、SDR、HDR/scRGB、负值/超白和
   UI premultiplication 差分。
4. **精度门禁**：medium identity/extinction、etaScale roulette 分布、packed tangent、area/SH
   direction、ray cone LOD 的误差与行为测试。
5. **alias/liveness test**：按 phase 图证明先写后读、覆写前最后消费者已完成、backend 切换不会
   读取旧 generation。
6. **显存账本 test**：静态合同字节数与运行时 VMA/native 分类统计对齐；resize/reload/switch 后
   无增长泄漏。

测试不得通过搜索源码函数名来证明行为，应观察生成产物、实际投影/颜色数值、GPU 结果和资源
计划。

### 15.3 benchmark 维度

后续 benchmark 至少固定并记录：

- GPU、driver、render/display extent、重建 backend、质量模式和场景 replay；
- 总显存 budget/usage、Prime VMA 分类、AS、纹理、wavefront、重建 targets、native pool；
- 各 pass GPU timestamp，尤其 trace queue、adapter、reconstruction、display；
- shader register、spill、instruction、occupancy 和编译闭包；
- 实际读写字节/cache 指标（设备支持时）；
- 图像/数学/统计正确性结果。

场景组应包含常见 replay、透明/流体/overlay、复杂纹理包、动态实体、极端分叉和高 render extent。
优化只有在相同输出契约、相同场景和相同分辨率下比较才有意义。

### 阶段 0：只设计并定稿规范

状态：**已完成（2026-08-31）**。规范来源为[渲染核心数据 IR](渲染核心数据IR.md)；本阶段未
修改生产行为、ABI 或测试。

- 编写规范性的 `渲染核心数据IR.md`，逐项冻结 IR 分层、术语、所有权和转换 owner；
- 定稿 NVIDIA 主路径的图像原点、像素中心、jitter、motion、depth、矩阵和无效值；

- 定义 semantic、encoding、binding、lifetime 和 alias schema，以及 Java/Slang 的约束方式；

阶段 0 完成的判据是维护者无需阅读具体 pass 就能确定任一常用数据的语义、编码候选、最低精度、

## 17. 验收原则

- 语义必须唯一且受约束；编码可以复用，也可以按阶段变化，但每次编码转换都有 owner 和误差合同。
- NVIDIA 主路径直接消费核心 IR；兼容路径承担不可避免的 adapter，不让低优先级回退定义全局规范。
- 不改变几何可见性、source identity、介质拓扑和 OpenPBR 数学来换性能；随机事件若受量化影响，
  必须满足事先定稿的分布/图像误差而不能只证明期望无偏。
- 不以覆盖率或结构体变小替代行为、分布、图像和真实 GPU 测量。
- 不为纯类型安全增加全尺寸图像；通过 schema、typed view 和 alias plan 表达。为 linear Rec.2020
  canonical texture 等正确性边界引入的数据由编码和生命周期优化回收，不能以旧 atlas 省空间为由
  放弃规范。
- 只把能让 RR/Streamline 直接使用、且在核心数学上正确的 NVIDIA 约定纳入 IR；opaque native
  layout、handle 和 SDK 私有 packing 仍留在 interop。
- 静态正确性转换应前移；纯性能转换仍须核算副本、上传、record stride、cache 和 shader ALU。
- 每次格式/精度变化必须给出数据合同 diff、显存账本、GPU benchmark 和相应正确性门禁。
- 实施顺序固定为规范定稿、测试/测量、生产迁移；测试不能以偶然现状替代规范决策。

## 18. 最终判断

Prime 现在最需要的不是立刻选择一套新的压缩格式，而是把材质 IR 扩展成覆盖整个 renderer core
的规范。该规范先确定 NVIDIA-aligned 坐标/重建形态、linear Rec.2020 texture 边界、语义/编码
分离、最低信息要求和约束 API；随后才由测试、账本和 benchmark 选择具体编码并迁移实现。

完成规范和门禁后，性能优化的重点会非常清楚：

1. wavefront 和重建 targets 决定按分辨率增长的显存门槛；
2. starmap 决定明显的固定显存与启动峰值；
3. texture/material 与 display adapter 决定可测量的热路径重复转换；
4. source texture 色彩转换、medium、etaScale、alias 和通道过载决定正确性与维护风险；
5. NVIDIA 主路径坐标对齐决定哪些全屏 adapter 可以被永久删除。

这套顺序可以让后续统一真正“一劳永逸”：核心语义只定义一次，编码按信息需求选择，CPU 翻译
执行静态正确性转换，GPU 热路径只保留帧/路径必需计算，RR/Streamline 尽量零转换消费，兼容
SDK 的差异只在边界出现，并且每个字节、转换和精度折衷都有可验证的来源。
