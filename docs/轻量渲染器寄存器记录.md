# 轻量渲染器寄存器记录

## 目的与当前决策

Lambert 只提供性能和光传输基线，目标画质需要继续增加材质能力。L1 之后用户确认运行正常，下一步已分析路径阶段复用并接入 RR/subgroup；当时路径为 128 B；2026-09-06 灯光与透明版本已采用 144 B 单路径及 48 B 暂存，见文末实施记录。早期布局候选见[路径记录复用分析](轻量路径记录复用分析.md)。功能增加时继续记录寄存器增长，防止在没有归因的情况下重新接近旧路径的高峰。

本记录不是人为设置的寄存器硬上限，也不要求为降低数字牺牲吞吐、引入 spill 或拆出更多 dispatch。物理寄存器由驱动编译决定；源码 struct 大小、SPIR-V ID 数和字节大小不能代替测量。

## 为什么很少源码也会有 60–80 live

需要同时看三层：当前算法的临时量、调用上下文仍需使用的数据、RT 编译生成的状态与代码。源级函数归属显示该范围内的峰值，不代表该函数独立拥有这么多局部变量。

本次最有力的内部对照是：只写一个距离值的 miss 为 **45 live / 82 allocated**；完全不做 position fetch 或纹理采样的 opaque any-hit 为 **57 / 85**。完整 any-hit 的 87 因此不能全部归到顶点、UV 或 alpha 算术。

any-hit 在遍历尚未结束时运行，接受/拒绝候选后需要继续遍历；其上下文与遍历完成后的 closest-hit 不同。NVIDIA 也明确指出 any-hit 位于调用图寄存器压力很高的位置。[NVIDIA RT best practices](https://developer.nvidia.com/blog/rtx-best-practices/)

这支持存在 RT 上下文贡献，但当前没有 SASS 的逐寄存器定义/使用关系或受控空 shader 实验，**不能精确宣称其中 45 个是驱动保留、剩下 42 个是用户代码**。world 与 shadow payload 分别为 64 B / 12 B，any-hit 却只差 1 live，也反驳了直接按 payload 字节数推算差额的办法。

### 大气：两个查询实际是八次 float4 image load

同一个 `atmSample2D` 在本次 shade 的不同调用范围内报告：

| 上下文 | live 峰值 | Top-Down CSV 行 |
| --- | ---: | ---: |
| 天空查询 | 48 | 26 |
| 星图的大气透射 | 61 | 42 |
| 太阳 NEE 的大气透射 | 62 | 12 |

这些是同一 helper 在不同上下文中的测量，不能把 62 解释为双线性采样的固定成本，也不能把 62−48 精确分配给某一组变量。

2026-09-05 对本地构建产物的 SPIR-V 反汇编确认：

- 生产 artifact 中这些 helper 已内联到 `main`，不存在通过改成另一个普通函数就能清空寄存器的调用边界。
- 太阳阴影 trace 返回后，先读出 albedo，再进入大气查询；albedo 三分量的结果在查询完成后才用于 direct。延迟到 trace 后加载并不等于已经延迟到所有昂贵子计算之后。
- low/high 两张表分别执行 `OpImageQuerySize`、坐标映射、四个夹紧后的 `int2` 地址、四次 `OpImageRead %v4float` 和三次向量插值。low 的四分量结果跨越 high 的整段坐标计算与插值，随后才与 high 一起转换颜色。
- 当前 SPIR-V 确实重复计算两张表的尺寸和采样坐标，没有把两张同域表表示为一次共享坐标的配对查询。
- 光谱矩阵、太阳光谱和 clear 归一化倒数已经是 SPIR-V 常量。不能按源码中的两个 `float3x4` 加一个 `float3x3` 就声称 33 个系数全占动态寄存器，也不能指望简单搬出这些常量就解决峰值。

因此实际重叠的是读取地址/插值数据、前一张表的结果和调用者后续工作需要的值。**八次 load 不等于八个 texel 一直同时存活**；真实发射次序、结果等待和寄存器复用仍由 NVIDIA 后端决定。62 有可解释的来源，但不应视为不可降低的最低需求。

首先值得验证的改动是让 albedo 在大气结果之后加载、共享配对查询坐标，以及减少不必要的中间量重叠。硬件过滤另作可审计的实验：需要核对格式支持、边界和插值误差；当前只确认手工过滤展开，未修改实现。

### Any-hit：提前展开的不是几个顶点变量

本地 world any-hit 的 SPIR-V 提供了比源码 struct 大小更明确的证据：

1. **进入源身份分支前已读取 section 的 9 个成员**：3 个 u64 地址与 6 个 u32 控制/计数字段。按信息宽度是 12 个 32 位字，但不是 12 个物理 live 的测量。部分地址只供后续材质/relation 使用，却在身份检查前已经出现。
2. **加载 primitive 的 7 个 u32 字段后才获取顶点**。这些字段随后供 recipe、UV 和 relation 解析消费，跨越了几何计算。第 8 个 tangent 字段已被裁掉，说明不能把完整 32 B record 无条件计入动态状态。
3. **顶点展开仍早于 repeated-UV 判断**。产物包含三个顶点读取、边向量、重心位置、ObjectToWorld 矩阵读取、affine 分支、叉积、缩放与 normalize，之后才进入材质/relation 判断和 alpha 查询。矩阵读取在当前 IR 中也位于 affine 分支之前。
4. **并非完整 `PrimeHitTriangle` 都存活**。any-hit 不消费世界 position，相关位置变换已消失；全局 triangleIndex 的几何返回部分也未形成有效计算。仍保留的是供投影 UV 使用的局部位置与法线计算，不能继续用该 struct 的 40 B 当成本。
5. **overlay 使同一 alpha 求值具有不同外围状态**。最终 alpha 查询的 live 为 **61**，relation 内部覆盖测试为 **87**；阴影对应 **60 / 86**。后者还必须保留用于选择主材质/回落材质、完成后续解析的数据。这 26 的上下文差值是观察值，不是 relation 固定占用 26 个寄存器的证明。

Top-Down 中，world any-hit 的源身份检查范围本身已有约 **79–80 live**，之后的顶点获取才到 87。这尤其说明“87 是 position fetch 一条操作用掉的寄存器”不成立。更合理的调查对象是**section 与材质提前加载、几何临时量和 RT 上下文的叠加**。

常量 UV / 普通重心 UV 不需要顶点位置或法线；repeated UV 需要的也只是实际投影所需信息。应让候选解析按消费者展开数据，而不是先生成完整表面再只取 alpha。但 overlay/双面关系与动态路径必须维持语义，后端可能进一步移动或删除 SPIR-V 操作；真实节省需要最终指令和 A/B 验证。

记录规则：

- 保存原 CSV、shader hash、源码/产物版本、GPU/驱动/编译参数、精确内部 extent、场景和重建模式。分场景捕获可以补热点覆盖，但不当作速度 A/B。
- 每次记录相对上一版的 live 与 allocated 增量；二者变化不同要分别解释。不要只记录全管线最大值，使其他 shader 的持续增长被 87 的总峰值掩盖。
- 峰值增长必须给出新增存活状态或计算来源；若理论 warps 降档、出现 spill，或 RT live state 增长，附上该阶段的时间与原因。暂不设置凭空选出的 64/80/96 硬门槛。
- 对照组优先保持相同 entry 和 RT pipeline 的调用环境。删除某项查询的诊断变体仅用于归因，不能以画面改变后的帧率作为生产优化验收。
- 如需精确回答 87 中每一部分的份额，下一份捕获应保留 Source/SASS 的 Live Registers、producer/consumer 依赖，以及相同 pipeline 下最小 any-hit 对照。当前结论明确区分已测数值、IR 数据流和未验证推断。

以上是 L0 捕获时的基线；下面的 L1 已修改生产实现，尚无新的 Nsight 寄存器捕获。

## 设计依据：共享摄像机大气近似与按需候选解析

2026-09-05 用户明确：太阳、天空和星图全部保留方向依赖，只把大气观察位置统一为摄像机；这一空间近似适用于所有渲染器。本节保留设计依据；实现与验证状态见文末 L1。

### 将大气观察位置固定为摄像机

空间近似定义为 `T_atmosphere(x, ω) ≈ T_atmosphere(camera, ω)`，取代每个命中位置的海拔修正。太阳、天空和星图的辐亮度仍分别是方向的函数，不使用太阳中心的单一 RGB 替代方向查询。当前消费代码本来就只用 Y 差值，没有按水平距离计算曲率海拔。这个近似放弃可见地形内的逐位置大气差异，将其解释为场景共享的远方光源条件，不改变 BSDF、表面法线响应、采样 PDF 或逐表面几何阴影。

不能把“几百米高差”视为所有情况下都严格无影响：低太阳高度角时的光程与近地密度变化更敏感。该限制应作为全局近似的画质边界记录，不以当前有限场景推导统一误差上限。

现有实现已经预计算以下资源，并非在每个 hit 上重新积分完整大气：

| 现有资源 | 当前尺度 / 内容 | 后续处理 |
| --- | --- | --- |
| transmittance low/high | 两张 256×64，8 波段透射率 | 保留在大气预计算阶段，移出普通照明消费闭包 |
| multiple scattering low/high | 两张 64×64 | 保留现有预计算 |
| sky view | 256×256，摄像机条件下的 Rec.2020 天空辐亮度 | 继续共享，避免重复建另一套天空 |
| aerial radiance / transmittance | 既有 3D 表，方向与距离相关 | 保留距离维度与现有更新/阴影依赖 |

原理与现有 Hillaire 型 sky-view / aerial LUT 架构一致：[Hillaire 2020](https://sebh.github.io/publications/egsr2020.pdf)。本项目当前额外的逐 hit 开销在于高度映射、光谱透射的手工过滤与 RGB 转换；仅把 `surfacePosition.y` 改为 camera Y 还不能消除这些工作。

可消费的数据应在现有 `AtmospherePipeline` 生命周期内准备：

- 太阳与星图共享摄像机高度下的方向透射查询；保留日落时太阳盘内的方向差异。普通 hit 只查最终 RGB，不再取两张光谱表。固定海拔后径向大气的透射率只依赖方向的竖直分量，可以使用小型一维 LUT；其采样参数化与分辨率必须覆盖近地平线的变化。
- 太阳盘辐亮度、星图源辐亮度各自乘实际方向的透射率。星图不能使用太阳方向的透射值，也不把二者合成同一个无方向光源。
- 天空继续使用摄像机条件下的二维 sky-view LUT，保留视线与太阳之间的方向关系。统一近似和消费边界不要求把天空、星图、透射率强行装进同一物理纹理。
- 对有限角太阳，NEE 和相机/BSDF 命中太阳必须消费同一套辐亮度定义，太阳盘 PDF 保持一致；地平线遮挡按采样方向处理，不能因为中心方向落下地平线就把仍露出的整块圆盘突然关掉。
- 空气透视是路径段的衰减和入射散射，不能退化成一份全局 RGB。现有 `L_out = T(view, distance) * L_surface + S(view, distance)` 的方向/距离表继续承担这项工作；视线相关体积阴影也不能由全局太阳色替代。

共享数据按实际依赖更新：方向透射依赖摄像机海拔和大气参数，sky-view 还依赖太阳高度，星图方向变换依赖天文参数。复用现有提交成功才发布、放弃提交不更新历史的所有权与同步。摄像机水平移动不必使纯方向透射重新生成，但 aerial 的投影和阴影更新仍依现有 key。离线与实时消费同一近似，避免相互作为参考时出现模型差异；当前仅输出材质颜色的 primary 模式不因此新增照明功能。

优先把预计算放进现有大气更新阶段，不默认新增每帧 GPU readback、CPU 第二套光谱实现或每种渲染器各自维护的缓存。RGB 查表和全局字段同样必须检查最终寄存器分配，不能仅以源码变短认定性能收益。

### any-hit 外围状态的来源与缩短办法

需要区分以下来源：

1. **驱动遍历上下文。** any-hit 位于仍可继续遍历的位置；相关状态来自 RT 执行机制，源码函数不能直接结束它的生命周期。当前 CSV 不暴露其逐寄存器组成。
2. **payload / attributes / shader 接口。** 源身份、重心等来自调用接口。raygen 报告的 0/4 B 是跨 trace 保存状态指标，不能据此认为 any-hit 没有输入或驱动上下文，也不能断言它把整个 Lambert path 一直保留在寄存器中。
3. **应用提前加载的数据。** section 的材质地址跨身份判断、primitive 跨几何展开、relation 的回落材质跨 overlay coverage 查询，都来自当前应用的数据流，可以针对性缩短。

按消费者组织数据类型、函数和读取顺序。手动拆函数可以改变 Slang 的特化与中间代码生成，应作为实际优化手段；关键是形成窄输入/输出和算法，而不是仍然在拆出的函数里构造同一个通用表面对象：

| 阶段 | 此时需要的数据 | 应推迟的数据 |
| --- | --- | --- |
| 检查 instance/source 身份 | 精确身份与该分支所需的三角形映射整数 | 材质、light、relation 地址与记录 |
| 接受已确认的 opaque 候选 | geometry class；必要时已完成的源身份结果 | 完整 surface 与纹理 |
| 判定 relation 类型 / coverage 是否必要 | 小型控制字、身份/偏移 | 尚未选中的回落材质内容 |
| overlay coverage / 最终 alpha | 实际纹理、UV 和当前所需的几何 | 后续才消费的 shading、透射与介质数据 |
| 仅当实际 UV 需要投影 | BLAS 顶点与所需投影信息 | 不消费的世界位置、完整 shading frame |

具体可先检查：让 `InstanceID()` 的比较先于 `SectionRecord` 展开；身份函数只取几个所需整数；先读取 relation 控制和偏移，必要时再读取回落材质；在实际需要 repeated UV 的分支内才做几何重建。现有旧 world any-hit 已有无 relation 的 transparent 早退，Lambert 候选路径尚未同样充分利用这些分类事实，值得按 Lambert coverage 语义审查复用。

这些变化不需要新的路径编码、每三角形属性副本或额外 dispatch。它们有机会同时减少读取次数和状态重叠，但不承诺 87 必然降到某个值；分别比较最小改动的 SPIR-V、最终 SASS、live、allocated、spill 和 GPU 时间，记录回落路径与峰值是否换了位置。驱动调度可以调整，但消除无关数据和不可达算法首先由源码特化负责。

### Slang 特化的实施依据

用户报告曾通过手动拆分函数使 SPIR-V 体积减少约 50%、帧率提升约 30%。这是用户提供的历史实测背景，不是本次 Lambert 的 A/B 结果；它说明不能把自动字段裁剪、常量传播和不可达分支删除作为设计前提。统一规则见[生产 Shader 编译边界契约](生产Shader编译边界契约.md)，本节只记录当前候选解析的应用。

- 身份查询使用只含精确映射所需字段的输入；coverage 使用只含实际 UV、纹理身份和控制的输入；只有需要投影的路径才获得投影几何。禁止先构造 `SectionRecord` / `PrimeHitTriangle` / `PrimeResolvedSurface` 全量临时对象，再期待后端删字段。
- 静态规范纹理与动态纹理、普通重心 UV 与投影 UV、无 relation 与 overlay/bilateral，按已经确定的事实进入实际需要的专用函数。运行时才知道的分类在边界判断一次，内部不重复经过全功能 dispatcher。
- 明确区分持久 GPU record 和消费端临时类型：固定 32 B 的 primitive 存储和共享 SurfaceKey 表可以保持原状，窄 accessor 按字段取数。这不要求为每个特化增加永久 GPU 副本。
- 手动单态化或有限代码生成都应形成可检查的具体函数与类型；仅给通用函数传 `false`、使用泛型或标记 inline，不能作为对应代码已消失的证据。共有数学仍使用同一窄叶，避免行为分叉。
- 变体只覆盖实际存在且能切掉成本的组合，先在当前 entry/dispatch 内完成，不枚举所有开关的笛卡尔积。
- 记录特化前后相同调试设置的完整 artifact 字节数、排除非语义调试内容的函数体规模，以及寄存器和运行时间。源码闭包、SPIR-V 和驱动结果分别验收；任意一项改善都不能直接代替另外两项。

### 全局候选解析

- Lambert、primary 颜色、旧实时/离线 world any-hit 使用共同的窄覆盖率路径；旧实时/离线
  shadow any-hit 也使用该路径，并将玻璃/水的消光、世界法线、相邻介质数据延后到实际需要时。
- 持久 `PrimitiveRecord` 仍为 32 bytes。候选仅携带直接记录、SurfaceKey 或关系材质的 16-byte
  句柄，分组读取 3 个 header 字和 4 个 UV 字；不逐字段引入重复的布局分支。
- 先读关系 discriminator，决定双面/overlay 表面。备用 UV、core 等只在选中后读取。primary
  alpha 成功的值保留供最终覆盖率或玻璃判断复用；选中备用材质时明确使该缓存失效。
- 常量/重心 UV 不取 BLAS 顶点；重复 UV 才取提交给 BLAS 的 f32 顶点和硬件重心，保持原来的
  局部位置、仿射法线、最大分量缩放、归一化及轴相等时的选择顺序。没有 epsilon、身份截断或
  图元宽泛忽略。opacity 的静态/动态纹理查询分为独立函数，只返回 mip-0 alpha。
- 不透明阴影 any-hit 按已绑定的 geometry class 0 特化源身份与 emitter 查询，只读不透明
