# 地形几何显存压缩设计

本文记录已实现的地形几何显存压缩布局及仍待完成的场景验收。强制 position fetch、静态输入
退休和全局 SurfaceKey 已进入生产代码；64 区块净显存、帧时间和固定路径图像对比尚未实测。
实现遵守[渲染核心数据 IR](渲染核心数据IR.md)、
[GPU 几何追踪精度契约](GPU几何追踪精度契约.md)和
[区块簇场景翻译架构](区块簇场景翻译架构.md)。

## 1. 背景与目标

在测试存档把视距提高到 64 区块后，Java 进程的 Windows 专用显存计数从约 3.3 GiB 随地形
驻留增长到约 11.7 GiB。当前资源包的材质纹理日志为：

- base page：44,695,552 bytes；
- normal page：4 bytes；
- optical page：4 bytes；
- texture records：40,960 bytes；
- animation cache：36,762,528 bytes；
- 合计约 77.7 MiB。

Windows 进程计数同时包含 Prime Vulkan、Minecraft 和其他同进程图形资源，因此该数值不能直接
归因到某一种 Prime 分配。视距相关性和纹理规模说明地形常驻资源是首要调查对象，但实施压缩前
仍需建立按用途统计的显存账本，并区分装载峰值与 BLAS 压缩完成后的稳态。

本设计的取舍已经明确：

1. 正确性、几何精度、身份、UV、材质和 surface relation 契约保持不变；
2. 显存是进一步提高视距的实质性瓶颈，优先压缩随地形图元数量线性增长的常驻数据；
3. position fetch 的净显存收益可以交换少量帧率损失，不以帧率零回退作为本项准入条件；
4. 跨 cluster 共享表预计较小，优先固定、保守的元素大小与直接索引，不为压缩小表增加复杂解码；
5. 不设置场景内容硬门限，不因压缩主动丢弃合法图元；保持 cluster 原子替换与明确的单一所有者。

用户此前测量显示去重表本身不会很大。本设计采用这一工作负载依据，但不把未在本次复测的
表大小或非矩形比例当作已验证数字。全局去重是选定方向，统计用于验证容量、定位剩余冗余，
不再把跨 cluster 共享后置为可选方案。

目标生产布局为：强制 BLAS position fetch，退休全部静态 BLAS 输入顶点，每个逻辑图元一个
4 B 全局 SurfaceKey，全局固定步长数组保存完整记录。常驻 MacroRectangleRecord、cluster-local
GPU surface 副本和按去重率切换 direct/keyed 的静态策略不进入目标实现。

本文不以降低纹理分辨率、裁剪远处地形、LOD 替换、量化任意斜面或 procedural AABB 求交换取
显存。设备功能缺失必须在初始化时明确报告；实际资源或地址范围不足必须在发布前明确处理，
不能截断索引、复用仍在使用的 key 或漏画。

## 2. 迁移基线的拓扑与存储

地形以对齐的 `4×4×4` Section cluster 为替换和 BLAS 生命周期单位。单个构建 segment 目标不
超过 128 Ki 个三角形或约 16 MiB CPU 输入，但该值只划分工作，不限制场景总几何。

### 2.1 已有矩形合并

满足以下条件的单位面会进入 `MergedFaceMeshBuilder`：

- 面可合并且是轴对齐平面；
- 平面坐标可吸附到 cluster-local `1/16` 网格；
- 投影范围是一个方块格；
- 没有 surface relation、水、方块发光或材质发光；
- normal、UV 和材质满足合并契约。

上述条件是单位面的入口约束；后续 `addComposite` 还会生成带 overlay relation 的共享矩形记录，
不能把所有 macro 图元视为无 relation。

相同平面轴、法线方向、平面坐标和完整材质语义的面先分组。opaque 和 transmissive 组在每个
`64×64` 平面上使用最优矩形分解；cutout 组因为 OMM 重复纹理的等级契约，当前只使用
`4×4`、`2×2` 和 `1×1` 方形模板。

每个合并矩形仍向 Vulkan BLAS 提交两个三角形，但两个相邻硬件三角形已经共享一条逻辑
`PrimitiveRecord`。shader 依据 geometry 内的 macro tail 将相邻 pair 映射到同一逻辑
图元；pair 内序号是 `(PrimitiveIndex - macroBase) & 1`，不能直接取 `PrimitiveIndex` 奇偶。
因此“把两个三角形合并为一个矩形记录”已经存在，后续设计必须复用该映射，不能为两个
硬件三角形重复存储相同 key。

### 2.2 当前字节数

`CpuMeshSegment` 当前使用非索引三角形列表：每个三角形固定保存 9 个 f32。一个普通合并矩形
的显式常驻输入为：

| 内容 | 数量 | 字节数 |
|---|---:|---:|
| BLAS/shader f32 顶点 | 2 triangles × 3 vertices × 3 components | 72 B |
| 共享 `PrimitiveRecord` | 1 × 8 u32 | 32 B |
| 合计，不含 BLAS/OMM/分配对齐 | | 104 B |

不能进入 macro 路径的普通 quad 通常保存两个三角形和两条 `PrimitiveRecord`，即 136 B，不含
surface relation、OMM 和 BLAS 本体。

当前 32-byte `PrimitiveRecord` 包含：

| 字段 | 大小 | 语义 |
|---|---:|---|
| `uv0/uv1/uv2` | 12 B | 三个投影角的 sprite-local UV 或常量材质数据 |
| `tint` | 4 B | tint 身份与控制位 |
| `identity` | 4 B | 材质/介质相关离散身份 |
| `flagsEmitter` | 4 B | 控制位、静态纹理或 cluster-local emitter 信息 |
| `uvDensity` | 4 B | UV 密度及周期/常量标记 |
| `tangent` | 4 B | 几何切线 frame |

纯材质身份已经通过 renderer-lifetime `MaterialId` 指向 8-byte `MaterialCoreRecord`，后者保存
`TextureId`、recipe control 和 `MediumId`。新的去重层不应复制或替代这一层，而应去重仍随逻辑
图元重复的 surface 数据。

### 2.3 BLAS 与构建期资源

BLAS 是除上述显式缓冲外的另一份常驻硬件结构。静态 BLAS 已启用异步 compaction；同时在途的
compaction target 总额限制为 64 MiB。source 和 target 在发布及退休窗口内短暂共存，未压缩
source 也可能在大规模装载期间积压，但 target 并发本身不能解释数 GiB 的额外常驻。

scratch 在 BLAS 构建完成后退休。position buffer 当前不能退休，因为 closest-hit/any-hit 从该
缓冲和硬件 f32 重心坐标重建权威命中位置。这使每个合并矩形的 72 B 顶点即使在 BLAS 已自包含
后仍然常驻。

## 3. 强制 position fetch，退休全部静态输入顶点

### 3.1 设备与 Shader 合同

目标生产设备必须支持并启用 `VK_KHR_ray_tracing_position_fetch` 及
`VkPhysicalDeviceRayTracingPositionFetchFeaturesKHR::rayTracingPositionFetch`。所有被 position fetch
访问的 BLAS，在尺寸查询和实际构建中都设置
`VK_BUILD_ACCELERATION_STRUCTURE_ALLOW_DATA_ACCESS_BIT_KHR`，保留所需的 compaction flag。
缺少功能时初始化明确失败，不维护无扩展的常驻顶点兼容路径。

closest-hit/any-hit 从 `HitTriangleVertexPositionsKHR` 获取当前命中的三个对象空间顶点，
随后保持现有边向量、硬件 f32 重心插值、ObjectToWorld 变换和几何法线计算顺序。硬件
triangle/geometry 索引和 macro 映射保持不变，不用射线算术命中点或独立 authored normal 代替。

当前 BLAS 的 geometry transform 为 null；实例变换仍在命中重建中显式处理。扩展规范返回应用
提供顺序的三角形顶点，但非空 geometry transform 的矩阵运算顺序未被完全指定，不能把这一
精度条件隐含掉。准入测试必须验证原始输入与 fetch 结果、compaction 前后的 f32 bit pattern、
winding、重心插值和命中身份。

规范来源：
[HitTriangleVertexPositionsKHR](https://docs.vulkan.org/refpages/latest/refpages/source/HitTriangleVertexPositionsKHR.html)、
[BLAS build flags](https://docs.vulkan.org/refpages/latest/refpages/source/VkBuildAccelerationStructureFlagBitsKHR.html)。

### 3.2 消费者与释放范围

| 数据或消费者 | 目标生命周期 |
|---|---|
| 静态主地形、流体、cutout、斜面及任意合法三角形的 BLAS 输入 positions | 最后一次 GPU build 读取完成后退休 |
| 静态实例原型与静态几何 fallback 的 BLAS 输入 positions | 同样退休，不因非矩形或共享原型而豁免 |
| 静态 closest-hit/any-hit | 只从 BLAS fetch 顶点 |
| 后续 compaction、TLAS 与 traversal | 不再引用原 positions buffer |
| 面光源采样使用的 LightEmitter 顶点/边向量 | 保留其独立采样生命周期，不阻碍原 positions 退休 |
| 动态运动重建使用的 positions 与上一帧变换 | 保留当前独立合同，后续单独迁移 |

当前静态位置读取集中在 `service/trace/hit.slang`；`math/packed_geometry.slang` 中另有后续
compute 阶段的动态运动重建读取。内建 fetch 只服务当前命中的 hit shader，不能按任意 triangle id
从 compute 随机读取 BLAS，不能据此直接删除动态重建数据。

本方案释放全部静态 BLAS 输入 positions，不需要把普通三角形和矩形拆成两种常驻 position
缓冲，也不需要增加 geometry、BLAS 或 TLAS instance。矩形几何描述不再有常驻消费者，直接
取消其 8 B/矩形存储；无需继续尝试 4 B 自包含几何编码。

### 3.3 构建与退休

CPU 翻译仍产生相同的权威 f32 三角形；首次迁移不改变 CPU 编码、构建输入顺序或 OMM 关联。
GPU input buffer 作为显式 build-only 资源，由构建事务拥有，并在其最后一次 GPU 读取完成后
通过既有延迟退休机制释放。不能在 CPU 记录或提交 build 时立即销毁，也不必等待 compaction
发布后才释放。

静态 resident binding 不再要求有效 positionAddress，不能保留假地址、空顶点流或永久占位分配
来维持旧的不变量。动态读取地址与静态 build-only 地址必须在类型或明确的布局状态中区分。
取消、构建失败、共享原型、cluster 替换与退出均沿同一所有权边界释放资源。

BLAS 构建完成后，输入和 scratch 在正确同步下可被复用或释放，见
[Vulkan acceleration structure 构建合同](https://docs.vulkan.org/spec/latest/chapters/accelstructures.html)。

## 4. 每逻辑图元一个全局 32-bit SurfaceKey

### 4.1 固定布局与读取

```text
hardware triangle -> existing macro mapping -> logical primitive -> SurfaceKey:u32
                                                                     |
                                                                     v
                                                   global PrimitiveRecord[SurfaceKey]

hardware hit -> BLAS position fetch -> authoritative position and geometric normal
```

每个 macro rectangle 只保存一个 key；普通三角形按现有逻辑 primitive 粒度保存一个 key。
所有静态图元使用相同的 key 寻址，包括无法合并、无法去重或带特殊 UV 的三角形，不为例外
增加逐图元 tagged union、变长索引或 direct/keyed 自适应布局。动态路径初期保留其现有直接记录。

SurfaceKey 是固定 u32 槽位索引，使用全部已声明索引位，不承担矩形几何描述或精确源身份。
不同物理表面可以共享 key；源/目标拒绝仍使用原有 section、triangle/逻辑 primitive 和 emitter
身份。禁止按相同 SurfaceKey 忽略相邻或共面但不同身份的面。

共享表直接复用现有 32 B `PrimitiveRecord` schema，不维护第二份同构 SurfaceRecord 定义。
GPU 通过全局 storage-buffer descriptor（set 0、binding 53）执行
`PrimitiveRecord[SurfaceKey]` 直接数组访问；表采用连续、固定步长数组，不使用 GPU
哈希、变长记录、分页指针链或按字段位宽分派。第一版保留完整保守字段，不为了少量共享表
显存增加 UV、切线等解码成本。以后调整共享元素大小需要独立更新 ABI 合同，不能改变当前
PrimitiveRecord 32 B 的约束。

固定存储大小不意味着每次读取整个记录。opaque 身份拒绝继续不访问 surface 表；只需要 emitter
或少数字段的消费者保持窄加载，完整命中可按实际访问合并加载。SurfaceKey 与几何 fetch 在
数据依赖允许时独立读取，不把全局表 accessor 扩展为包含纹理、关系、BSDF 的宽入口。
按消费者保持最小 Shader 编译闭包。

MaterialId 及其 8 B MaterialCoreRecord 继续承担原有全局材质语义；SurfaceKey 去重的是仍随
逻辑图元重复的表面数据，不复制材质表或把完整材质状态延长到后续 wavefront 阶段。

### 4.2 去重内容与局部绑定

首次迁移在 MaterialId、TintId、medium 与 GPU relation/emitter payload 全部解析后，对完整
32 B 最终记录逐位跨 cluster 去重；哈希只用于 CPU 查找，冲突由完整字段比较消解。保留所有
有意义的位模式，不通过浮点 epsilon、NaN 归一化或删除字段提高命中率。

当前 emitter 编号和 relation offset 仍按命中 section 解释。两个 cluster 中相同字节的记录可以
共享槽位，但同一 SurfaceKey 不保证跨 section 指向相同的 relation/emitter 对象。相同表面定义
因不同局部 payload 产生不同表项也是合法状态，不能把 payload 清零或误解释成全局身份。

诊断必须区分由 UV、tint、切线等表面数据造成的唯一项与仅由局部 payload 造成的分裂。
若后者主导共享表容量，再把可共享定义与局部绑定分离；该改造需显式更新 relation/emitter ABI
与行为测试，不能在本阶段以重复索引层或稀疏查找补丁实现。无论是否分离，GPU surface 表
始终跨 cluster 共享，不退回每 cluster 一份副本。

### 4.3 所有权、稳定 key 与空洞复用

全局 registry 由 renderer 拥有，所有可变状态集中在 render thread：CPU intern map、slot
内容、引用计数、free list、待退休项和 GPU 表容量。worker 只产生不可变输入，不直接修改
registry；本设计不增加跨线程共享 map、锁域或锁顺序。

每个不可变 GPU 几何所有者（cluster 或共享原型）持有一份 CPU 端唯一 key 集合，同一所有者
重复引用某个 key 只计一次。共享原型的 key lease 随原型资源生存，不按每个 instance 重复
获取。引用规则为：

1. 上传事务先取得 key lease 并完成新增槽位上传，再允许发布引用这些 key 的场景；
2. cluster 原子替换只转移所有权，旧资源及其 lease 保持到最后一次 GPU 读取完成；
3. 未提交的取消可直接释放事务 lease，已提交工作必须经过 GPU 完成后的退休；
4. 引用归零且最后一次 GPU 读取完成后，槽位才进入 free list，不能因 CPU 卸载提前复用；
5. 新表项优先复用空洞，没有空洞时才增加容量。

key 在所有有效引用期间稳定；完全退休后可被其他记录复用。同一内容日后重新加载不承诺
沿用原 key。现有 MaterialId、TextureId 等身份的独立稳定性合同不因此改变。GPU 无需每次
查表检查 slot generation，安全性由上传、发布和退休不变量保证。

允许容量中的空洞，不在线移动存活项，不为了填洞重写数百万图元 key。CPU map 和 slot 元数据
也要计入内存账本；不能在移除 GPU 记录后仍无用途地保留完整历史内容。

### 4.4 容量与地址

固定元素大小不等于一次分配完整 u32 地址空间。初版使用一个按容量增长的连续 GPU 数组，
保留适度余量，批量上传新增或安全复用的槽位；不每帧复制完整 surface 表。

扩容时保留 key 数值和 slot 位置，将必要内容复制到新 buffer。新帧使用新 table binding，
旧帧继续使用旧 buffer，旧 buffer 在最后一次使用后退休。表基地址属于 frame/global binding，
不能复制进每个 cluster 并因此让扩容触发全场景重写。单一 owner 必须保证扩容期间的新槽位写入
进入正确的 buffer，发布前上传完整；扩容新旧 buffer 共存计入峰值。

不引入在线压实、GPU 哈希或多层页表以降低这一预期较小数组的容量。只记录活跃槽位、待退休
槽位、可复用空洞和已分配容量，用实测说明余量成本。

初版 GPU 数组按两倍扩容，槽位不搬移；上传只写新增或安全复用的槽位，使用一份紧凑 staging
分配和相邻槽位合并成连续 region，每批最多 1024 个 copy region。当前数组走 storage-buffer descriptor，容量必须满足
`maxStorageBufferRange`；key 流仍走原来的 BDA。各自按实际寻址合同检查范围，字节偏移使用
64 位整数。无法表示或分配时在场景发布前明确失败，不少分配、不截断索引、不复用活跃槽位。

## 5. 利用矩形占多数的内容特征

MC 以矩形面为主，历史工作负载中全局 surface 表较小。这支持“窄图元引用 + 保守共享记录”
的布局，不要求把所有合法模型强制翻译为轴对齐 macro rectangle。

几何合并继续使用已有最优矩形/OMM 模板契约。源矩形数、已合并 macro 数和非 macro 数必须
分别统计：水、发光面、relation、非单位投影面等也可能是矩形，但不满足当前 macro 入口。
不能以非矩形稀少推导这些特殊语义同样稀少。

非 macro 图元的 positions 同样通过 fetch 退休；难以共享的记录自然占用唯一全局槽位，
不建立另一套任意三角形压缩器。若特殊逻辑图元占比为 q，并保守地认为它们全部无法去重，
其记录成本约为每个逻辑图元增加 32q B，另加常见共享项与容量余量。这是成本模型，不是已测比例。

不为了减少极少数例外的 32 B 表项，给所有常见命中增加变长解码、类型跳转、二次查找或额外
按图元常驻 metadata。例外比例上升时先定位字段和内容来源，完整保留合法图元。

## 6. 显存模型、账本与性能取舍

### 6.1 稳态显存

设 R 为 macro rectangle 数，T 为其余硬件三角形数，则逻辑 primitive 数 P = R + T，
硬件三角形数 H = 2R + T。C 为全局 surface 数组容量，包含活跃项、退休保护项、空洞和余量。

```text
current explicit geometry = 36H + 32P
target explicit geometry  = 4P + 32C
explicit saving           = 36H + 28P - 32C

total saving = explicit saving - (BLAS_fetch - BLAS_baseline)
```

最后一式仅在其他类别不变时成立；实际比较还必须加入 OMM、relation、light、TLAS、allocator
对齐与其他资源变化。不能默认启用 ALLOW_DATA_ACCESS 后的压缩 BLAS 大小保持不变。

| 图元 | 当前独立显式数据 | 目标独立引用，不含共享表摊销 |
|---|---:|---:|
| macro rectangle | 104 B | 4 B |
| 普通三角形 | 68 B | 4 B |
| 两个逻辑三角形的普通 quad | 136 B | 8 B |

macro 的 104 B → 4 B 对应独立显式数据减少约 96.2%，不是整机显存减少 96.2%。
总显存必须使用 C 而不是仅用活跃唯一数 U 计算。全局 surface 表即使有适度容量余量，只要规模
较小，也应优先保持访问速度；优化重点是 4P、BLAS/OMM 等随图元数量增长的项。

### 6.2 分配账本与峰值

按用途累计当前字节、峰值和分配数，至少区分：

- 静态 build input positions 与迁移期间尚未退休的旧 positions；
- 静态 key 数组，全局 surface 表的活跃、待退休、空洞、容量及扩容副本；
- surface relation、light emitter 与 light tree；
- OMM storage、build input、scratch；
- BLAS uncompacted source、compacted target、build scratch；
- TLAS backing、instances、SectionRecord、motion transform；
- 动态 positions、直接 primitive、motion 及实例原型；
- 纹理 pages、records、animation cache、renderer images；
- staging 和其他可归因的 Prime 分配。

同时报告资源请求字节、VMA allocation/block committed bytes，以及能够取得的设备预算/使用量。
Prime 账本不能假装完整覆盖 Minecraft 或其他同进程分配，无法归因的进程差额单独报告。

至少记录初入世界峰值、加载完成和全部 compaction/retirement 收敛后的稳态。源/目标 BLAS、
旧新 cluster、staging、build input 以及 table 扩容副本的共存必须计入峰值。
常驻位置退休不会减少首次 f32 build input；上传准入仍按真实构建工作集计费，不能按 4 B key
错误提高并行构建数量。保留现有流送回压，不按显存压力删除合法已驻留内容。

### 6.3 数据统计

按 opaque、cutout、transmissive 分别记录硬件三角形、逻辑图元、macro rectangle、源矩形与
其他几何数量，以及 position/key/relation/OMM/light 字节。记录全局 U、C、每 cluster 引用的
唯一 key 数、跨 cluster 重复规模、局部 payload 分裂和特殊记录占比。

去重模拟使用最终上传记录的完整位模式；可以通过 CPU 临时去重减少重复 registry 查找，但
不能因此在 GPU 恢复 cluster-local surface 数组。只报告全局实际字节和按字节加权的比例，
不使用各 cluster 去重率的简单平均代替总收益。

### 6.4 性能验收

本任务的已接受取舍是以少量帧率损失换取 position fetch 的显著净显存收益。几何正确性、
身份和所有权不可交换；不把任意幅度的性能下降归入“少量”，也不自动套用零回退门限。
本次未指定数值百分比，不虚构已获接受的 5% 或 10% 上限。实施报告必须给出明确实测差值、
波动范围与剩余瓶颈，明显超出少量损失的结果需要继续定位优化。

比较使用相同相机路径、驻留集合、分辨率、采样/反弹设置和资源包，至少区分：

- 稳态显存与装载峰值，启用 fetch 后压缩 BLAS 的实际体积；
- GPU 帧时间中位数和高分位，以及对应 FPS 变化；
- opaque、cutout/OMM unknown、transmissive 的 hit/any-hit 和完整路径时间；
- 全局表读取流量、可取得的 cache/寄存器指标，CPU intern、上传和加载完成时间。

更高视距另作容量实验，报告相同设备预算下能稳定承载的驻留规模；不把不同视距的 FPS 直接
归因为 position fetch 回退。GPU 利用率和独立 ray throughput 仅为辅助指标，不能代替帧时间
与净显存收益。

表内访问优先性能，不为节省少量 32C 引入复杂编码；随图元增长的常驻数据优先压缩。
本项取舍不授权近似几何、压缩精确身份，也不放宽无关 Shader 拆分和其他功能的性能契约。

## 7. 实施与验证状态

已实现：

1. 设备必须支持并启用 `VK_KHR_ray_tracing_position_fetch` / `rayTracingPositionFetch`。
   BLAS 尺寸查询与构建统一包含 `ALLOW_DATA_ACCESS`，其他 build policy 与 compaction 调度保持原合同。
2. hit stage 使用 BLAS object-space 顶点，保留原插值和法线运算。全部 owned 静态 BLAS 输入
   随构建 scratch 一同延迟退休；静态共享 voxel 原型同样适用。动态原型和借用的动态 fallback motion 顶点仍保留；
   原型池 key 包含 position lifetime，禁止静态/动态用途跨域取得同一 BLAS。
3. 静态 primitive 流替换为 4 B key；`SectionRecord.instanceTint` 的 bit 29 标识该布局。
   该标识属于 section，不占 key 位。动态直接记录保留，实例 tint、affine 和源图元身份不变。
4. `SurfaceRecords` 在 render thread 上对最终 32 B 记录做完整比较。每个 BLAS 分配持有唯一
   key 集合；GPU 完成回调只把已完成 lease 放入队列，render thread drain 后才释放引用、复用槽位。
5. `SurfaceTable` 批量上传变更；扩容保留索引，buffer binding 随 scene view 发布，旧 buffer 延迟
   退休。取消上传保留当前表；已提交的失败资源走 GPU 退休。共享原型只持有一份 lease。
6. 调试信息报告静态 key、BLAS、共享表实际容量和显式数据成本，以及 Prime VMA 的 allocation /
   block committed bytes（device-local heap 与其他 heap 分开）。VMA 快照按秒缓存，避免每帧扫描。

已通过 CPU 全量测试、生产 Shader ABI / 闭包检查，以及开启 Vulkan validation 的独立 GPU oracle。
GPU oracle 覆盖三个 geometry 分区、任意 f32 三角形、非零实例平移、两个 hit stage、释放输入后的
position fetch 与 compaction；还直接调用生产查表函数，逐位对比 keyed/direct 记录，验证奇数
macroBase、macro pair 与共享 key 的不同 triangle 身份。

2026-09-05 验证：`build`、`artifactTest` 与选定 GPU 回归通过；CPU 578 项、产物 1 项、GPU 14 项，
均无失败或跳过，Vulkan validation 无错误。重跑命令：

```powershell
.\gradlew.bat build artifactTest shaderTest --tests '*PositionFetchGpuTest' --tests '*PrimeNumericalGpuTest' --tests '*PrimeProductionMathGpuTest'
```

中的表扩容、取消与旧新帧共存压力测试；按用途进一步细分退休和构建峰值。当前诊断数字没有把
