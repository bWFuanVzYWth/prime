# 地形几何显存压缩设计

本文记录地形几何显存压缩的候选设计。它目前是待实施方案，不改变现有生产 ABI、场景语义或
追踪结果。实施时必须遵守[渲染核心数据 IR](渲染核心数据IR.md)、
[GPU 几何追踪精度契约](GPU几何追踪精度契约.md)和
[区块簇场景翻译架构](区块簇场景翻译架构.md)。

## 1. 背景与目标

在测试存档把视距提高到 64 区块后，Java 进程的 Windows 专用显存计数从约 3.3 GiB 随地形
驻留增长到约 11.7 GiB。当前资源包的材质纹理日志为：

- base page：44,695,552 bytes；
- normal page：4 bytes；
- optical page：4 bytes；
- texture records：40,960 bytes；
- animation cache：36,762,528 bytes；
- 合计约 77.7 MiB。

Windows 进程计数同时包含 Prime Vulkan、Minecraft 和其他同进程图形资源，因此该数值不能直接
归因到某一种 Prime 分配。视距相关性和纹理规模说明地形常驻资源是首要调查对象，但实施压缩前
仍需建立按用途统计的显存账本，并区分装载峰值与 BLAS 压缩完成后的稳态。

本设计的目标是：

1. 降低大视距下静态地形的常驻显存；
2. 减少命中路径读取的离散图元数据，同时保持可缓存性；
3. 保持提交给 BLAS 的三角形、winding、身份、UV、材质和 surface relation 语义不变；
4. 不设置场景内容硬门限，不因显存优化主动丢弃合法图元；
5. 把紧凑地形表示与通用三角形、动态场景和兼容 fallback 隔离，避免扩大初次改动范围。

本文不以降低纹理分辨率、裁剪远处地形、LOD 替换、量化任意斜面或 procedural AABB 求交换取
显存。硬件或地址空间的真实限制必须显式报告；仍可使用现有精确表示时应回退表示方式，而不是
停止渲染该图元。

## 2. 当前拓扑与存储

地形以对齐的 `4×4×4` Section cluster 为替换和 BLAS 生命周期单位。单个构建 segment 目标不
超过 128 Ki 个三角形或约 16 MiB CPU 输入，但该值只划分工作，不限制场景总几何。

### 2.1 已有矩形合并

满足以下条件的单位面会进入 `MergedFaceMeshBuilder`：

- 面可合并且是轴对齐平面；
- 平面坐标可吸附到 cluster-local `1/16` 网格；
- 投影范围是一个方块格；
- 没有 surface relation、水、方块发光或材质发光；
- normal、UV 和材质满足合并契约。

相同平面轴、法线方向、平面坐标和完整材质语义的面先分组。opaque 和 transmissive 组在每个
`64×64` 平面上使用最优矩形分解；cutout 组因为 OMM 重复纹理的等级契约，当前只使用
`4×4`、`2×2` 和 `1×1` 方形模板。

每个合并矩形仍向 Vulkan BLAS 提交两个三角形，但两个相邻硬件三角形已经共享一条逻辑
`PrimitiveRecord`。shader 依据 geometry 内的 macro tail 和 `PrimitiveIndex` 奇偶关系恢复逻辑
图元索引。因此“把两个三角形合并为一个矩形记录”已经存在，后续设计必须复用该映射，不能为
两个硬件三角形重复存储相同 key。

### 2.2 当前字节数

`CpuMeshSegment` 当前使用非索引三角形列表：每个三角形固定保存 9 个 f32。一个普通合并矩形
的显式常驻输入为：

| 内容 | 数量 | 字节数 |
|---|---:|---:|
| BLAS/shader f32 顶点 | 2 triangles × 3 vertices × 3 components | 72 B |
| 共享 `PrimitiveRecord` | 1 × 8 u32 | 32 B |
| 合计，不含 BLAS/OMM/分配对齐 | | 104 B |

不能进入 macro 路径的普通 quad 通常保存两个三角形和两条 `PrimitiveRecord`，即 136 B，不含
surface relation、OMM 和 BLAS 本体。

当前 32-byte `PrimitiveRecord` 包含：

| 字段 | 大小 | 语义 |
|---|---:|---|
| `uv0/uv1/uv2` | 12 B | 三个投影角的 sprite-local UV 或常量材质数据 |
| `tint` | 4 B | tint 身份与控制位 |
| `identity` | 4 B | 材质/介质相关离散身份 |
| `flagsEmitter` | 4 B | 控制位、静态纹理或 cluster-local emitter 信息 |
| `uvDensity` | 4 B | UV 密度及周期/常量标记 |
| `tangent` | 4 B | 几何切线 frame |

纯材质身份已经通过 renderer-lifetime `MaterialId` 指向 8-byte `MaterialCoreRecord`，后者保存
`TextureId`、recipe control 和 `MediumId`。新的去重层不应复制或替代这一层，而应去重仍随逻辑
图元重复的 surface 数据。

### 2.3 BLAS 与构建期资源

BLAS 是除上述显式缓冲外的另一份常驻硬件结构。静态 BLAS 已启用异步 compaction；同时在途的
compaction target 总额限制为 64 MiB。source 和 target 在发布及退休窗口内短暂共存，未压缩
source 也可能在大规模装载期间积压，但 target 并发本身不能解释数 GiB 的额外常驻。

scratch 在 BLAS 构建完成后退休。position buffer 当前不能退休，因为 closest-hit/any-hit 从该
缓冲和硬件 f32 重心坐标重建权威命中位置。这使每个合并矩形的 72 B 顶点即使在 BLAS 已自包含
后仍然常驻。

## 3. 第一阶段：每逻辑图元一个 32-bit SurfaceKey

### 3.1 基本布局

将静态地形的逻辑 primitive 数组从 32-byte `PrimitiveRecord` 改为 32-bit `SurfaceKey` 数组：

```text
hardware triangle
  -> existing macro triangle mapping
  -> logical primitive index
  -> SurfaceKey
  -> deduplicated SurfaceRecord
```

一个 macro rectangle 只保存一个 key。不能按硬件三角形保存两个 key，否则会丢失现有宏图元
映射已经获得的空间收益。

第一版应保持 `SurfaceRecord` 与现有 `PrimitiveRecord` 位级同构，使改动集中在存储和寻址，
不同时重写材质语义。去重表优先由一个 immutable resident cluster 拥有：这样 emitter 和
surface relation 仍可保留 cluster-local 精确偏移，生命周期也与现有原子 cluster 替换一致。
纯材质继续通过全局 `MaterialId` 共享。只有实测证明跨 cluster 的 surface 重复值得额外生命周期
复杂度后，才考虑 renderer-lifetime 全局 intern 表。

动态、实例原型和 fallback 初期保留当前 32-byte 直接记录。静态地形的通用非 macro 三角形可以
使用相同 key 路径，但不要求与矩形描述改造同时完成。

### 3.2 收益边界

设 resident cluster 中有 `P` 条逻辑 primitive 引用，去重后有 `U` 条 32-byte 表项：

```text
current  = 32P
keyed    = 4P + 32U
benefit  <=> U / P < 0.875
```

对于 macro rectangle，仅替换记录时显式数据从 104 B 变为 76 B 加去重表摊销，理想上限是
26.9%。如果错误地为两个硬件三角形分别保存 key，则变为 80 B，且盈亏点下降到
`U / P < 0.75`。

实际总显存收益会小于显式输入缓冲收益，因为 BLAS、OMM、TLAS、纹理和其他图像不受此阶段
影响。额外一次依赖表读取可能增加单次命中延迟，但更窄的连续 key 流和更小、更热的去重表也
可能改善缓存命中；必须同时测量显存、主射线吞吐和完整路径吞吐。

### 3.3 稀有数据与溢出

“所有信息进入表”不能演变为静默丢弃 cluster-local 数据。带 emitter、surface relation、动态
纹理控制或其他不可全局共享状态的记录仍使用完整表项；cluster-local 去重允许这些表项自然
退化为唯一项，而不会改变语义。

32-bit key 是 GPU ABI 的表示范围，不是人为内容门限。key 空间、设备 buffer 地址范围或 Vulkan
最大 storage buffer range 真正不足时，构建必须在发布前检测，并将对应 segment 回退到现有
直接记录布局或进一步分段。只有设备不能表示现有精确路径时才能明确失败，不能漏画、复用错误
key 或截断索引。

## 4. 第二阶段：精确 MacroRectangleRecord

第一阶段最多移除每矩形 28 B 的重复记录，而当前更大的显式冗余是 72 B 非索引顶点。已进入
macro 路径的面拥有比任意三角形更强的精确约束，可以使用专用紧凑几何描述，而不量化通用
几何。

### 4.1 候选表示

一个 macro rectangle 可由以下离散量精确描述：

- plane axis 和 normal sign；
- `1/16` 网格上的 cluster-local plane cell；
- `64×64` 投影平面上的 `u`、`v` 起点；
- width 和 height；
- `SurfaceKey`。

几何字段可以装入两个 u32，key 单独保存为一个 u32。SoA 物理布局的逻辑成本约为
8 B descriptor + 4 B key，即 12 B/矩形；如果设备访问和对齐实测支持 16-byte AoS 更好，允许以
16 B 换取更简单或更快的读取，但必须记录真实分配结果。

### 4.2 构建与命中

BLAS 仍使用两个硬件三角形：

1. CPU 从离散描述生成与当前路径相同的六个 f32 顶点；
2. 该 f32 缓冲只作为 BLAS build input；
3. GPU 完成 build 后退休 f32 build input；
4. shader 根据 `MacroRectangleRecord`、三角形在 pair 内的序号和硬件重心坐标重建三个权威
   f32 顶点；
5. 命中位置、法线、源图元身份和运动语义继续遵守现有精度契约。

整数坐标和以 16 为分母的 dyadic 坐标在当前 cluster 范围内可以被 f32 精确表达，但这只是实施
可行性的依据，不代替验证。CPU build input 与 shader 重建必须共享明确的顶点顺序规范，并通过
原始 f32 bit pattern、三角形 winding、AABB 和重心插值行为测试证明一致。

该阶段把普通合并矩形的显式常驻数据从 104 B 降到约 12--16 B，理论上减少约
84.6%--88.5%，但 BLAS 本体仍保留。任意斜面、流体、非标准 quad、不能精确描述的模型和兼容
fallback 继续使用现有 f32 顶点流。

### 4.3 不采用 procedural rectangle

Vulkan ray tracing BLAS 没有原生 rectangle primitive。用 procedural AABB 加 intersection shader
可以把一个矩形表示为一个 AABB，但会增加自定义求交、调度、any-hit 和驱动路径成本，也可能
降低 traversal 吞吐。当前同时需要提高帧率，因此不把它作为主方案；除非独立原型在目标 GPU
上同时证明更低显存和不低于硬件三角形路径的吞吐，生产实现继续使用两个硬件三角形。

## 5. 实施前诊断

压缩实现前先建立以下只读统计，避免依据进程总显存猜测收益：

### 5.1 GPU 分配账本

按资源语义累计当前字节、历史峰值和分配数：

- static positions；
- static primitive/key/surface table；
- surface relation；
- OMM storage、build input 和 scratch；
- BLAS uncompacted source、compacted target 和 build scratch；
- TLAS backing、instances、SectionRecord 和 motion transform；
- dynamic prototype、dynamic fallback；
- material pages、records 和 animation cache；
- renderer images、Minecraft interop 和无法分类的其他分配。

账本同时报告请求大小和 VMA heap/block 级 committed bytes。前者可以归因资源，后者包含对齐和
allocator 空洞；两者不能混为同一数值。每次测试至少记录初入世界峰值、地形装载结束、所有
compaction query/ready/retirement 队列清空后的稳态。

### 5.2 拓扑与去重模拟

按 opaque、cutout、transmissive 分别报告：

- 硬件三角形数；
- macro triangle pair/rectangle 数；
- 非 macro 三角形数；
- position、primitive、relation 和 OMM 字节；
- 完整 32-byte surface record 的引用数和唯一数；
- `U/P`、第一阶段预测节省量；
- 可由精确 rectangle descriptor 表达的常驻 position 字节。

去重模拟应在 renderer-lifetime MaterialId、TintId 和 GPU surface relation 已解析后的最终上传
记录上进行，不能用翻译前对象身份或源码字段近似真实 GPU 内容。

## 6. 迁移顺序

1. 加入显存账本、拓扑统计和不改变上传内容的去重模拟；
2. 在 64 区块测试存档记录稳态基线，确认地形各项真实占比；
3. 为静态地形加入 cluster-local `SurfaceKey` 与同构 `SurfaceRecord` 表；
4. 验证主射线、any-hit、完整路径、surface relation、发光和 reload 后再测显存与性能；
5. 为 macro rectangle 加入精确描述和 shader 重建，构建完成后退休其 f32 positions；
6. 依据剩余占比决定是否为通用几何加入 indexed vertices、跨 cluster surface intern 或静态
   geometry arena。后两项会扩大生命周期和可变分配器复杂度，不应在没有数据时预先引入。

BLAS build flags、cluster 尺寸和 compaction 调度同时影响显存、追踪速度、重建成本和流送粒度，
不与数据布局改造捆绑。只有单变量对比证明收益后才调整。

## 7. 验收门禁

每一阶段必须通过：

- 全量构建和现有 CPU/GPU 行为测试；
- macro pair 到逻辑 primitive/key 的边界与随机属性测试；
- 原始 `PrimitiveRecord` 与 key/table 解码逐位一致；
- emitter、surface relation、cutout/OMM、透明边界和材质动画行为一致；
- CPU BLAS build 顶点与 shader rectangle 重建的 f32 bit pattern、winding 和身份一致；
- NaN/Inf、退化面、非法索引、buffer range、key 空间和设备上限验证；
- 资源 reload、cluster 原子替换、取消、退休和 compaction 生命周期无泄漏；
- 相同相机路径的图像与命中身份无差异；
- 64 区块稳态显存、装载峰值、帧时间、GPU 利用率和 ray throughput 对比。

性能收益不能替代正确性证明。若某类几何不能满足专用紧凑表示契约，它必须继续走当前精确
通用路径，而不是以相近矩形、固定 epsilon、截断身份或丢图元代替。
